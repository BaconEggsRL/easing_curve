# Easing Curve v1.0.9 Code Tracker

## 1. Release Charter [FROZEN]

### 1.1 User-confirmed v1.0.9 goals

The user confirmed the following goals for v1.0.9:

1. **Code-smells / architecture / performance / bug review**
   - identify code smells and architecture improvements for future
     maintainability;
   - identify meaningful speed/performance bottlenecks and worthwhile
     optimizations;
   - identify concrete program bugs discovered during the review;
   - do not assume every finding must be implemented in v1.0.9.

2. **Graph-toolbar point navigation / reordering controls**
   - add graph-toolbar arrows for selecting and/or reordering points;
   - if both navigation and reordering are exposed, keep their semantics
     visibly distinct rather than making one ambiguous arrow operation;
   - reuse existing point ordering, selection, identity, and Undo/Redo
     behavior rather than creating a second ordering model.

3. **Persist graph zoom and pan through project/editor restarts**
   - store graph view state with the `EasingCurve` resource so it survives
     editor/project restarts;
   - preserve the current per-resource ownership model;
   - review serialization/resource-dirty/source-control implications before
     implementation;
   - preferred direction from the accepted feature review is private
     storage-only resource state rather than visible public curve parameters.

4. **Curve-editor playback/sample preview**
   - add a playback bar, playhead, dot, or equivalent preview UI to the curve
     editor;
   - the preview must make the current normalized X value and the corresponding
     `EasingCurve.sample(x)` output visually understandable;
   - keep v1.0.9 preview focused on the easing curve itself rather than
     animating arbitrary scene properties.

## 2. Future Release Roadmap [FROZEN USER-SUPPLIED BOUNDARY]

The user explicitly moved the following features out of v1.0.9. These entries

### 2.1 Future / v1.0.10 — `MULTI-EDIT-01` — Multi-point editing

**Status:** FUTURE / NOT ACTIVE

#### User goal

Support multi-point editing, with Shift-drag potentially acting as a selection
rectangle. Intended batch operations include:

- selecting multiple graph points;
- deleting selected points;
- updating Handle Mode across the selection;
- updating control state/mode across the selection;
- translating selected points together.

#### Agreed release rationale

This should be treated as a dedicated release-level feature rather than folded
into v1.0.9 because current graph/Inspector selection is fundamentally
single-point oriented.

The difficult part is not drawing the selection rectangle; it is introducing a
coherent multi-selection model across:

- graph selection/highlighting;
- Inspector state;
- point Resource identity through reorder;
- batch translation/order/endpoint behavior;
- batch Handle Mode/control-state editing;
- atomic Undo/Redo;
- selection restoration through Undo/Redo and Inspector refresh.

#### Existing architectural reservation

v1.0.8 deliberately leaves pre-held Shift unconsumed by the initial axis-drag
hold. Preserve that reservation unless a later multi-selection design explicitly
changes it.

### 2.2 Future / v1.0.10 or later — `ANIMATION-TARGET-01` — Node/property assignment

**Status:** FUTURE / NOT ACTIVE

#### User goal

Add AnimationPlayer-like assignment of easing behavior to a Node/property, such
as:

- position;
- rotation;
- scale;
- other supported animatable properties.

#### Agreed architectural direction

Do not assume Node/property target metadata belongs directly on `EasingCurve`.
`EasingCurve` should remain the reusable interpolation/geometry resource.

A future design should evaluate a separate track/animation abstraction, for
example conceptually:

```text
EasingCurve
    -> normalized interpolation

Easing animation/track resource
    -> target Node/property
    -> from/to values
    -> timing
    -> EasingCurve reference
```

The exact class/resource/API is not yet frozen and requires its own architecture
review before implementation.

#### Major design questions for that future release

- target path ownership and root-relative semantics;
- node rename/path resilience;
- local versus global transforms;
- supported property types;
- from/to value ownership and absolute/relative modes;
- reusable curves across multiple targets;
- safe editor preview/revert behavior;
- runtime versus editor-only responsibility;
- Undo/Redo behavior;
- external `.tres` resources shared across scenes.

### 2.3 Future / v1.0.10 or later — `ANIMATION-TIMING-01` — Duration / speed

**Status:** FUTURE / NOT ACTIVE

#### User goal

Add speed/duration parameters for animations.

#### Agreed architectural direction

Duration/speed does not transform the easing function in the same way as
`reverse` or `invert` and therefore should not be treated as an `EasingCurve`
Global Transform merely because that Inspector group already exists.

Normalized easing remains conceptually:

```text
elapsed time / duration
    -> normalized x
    -> EasingCurve.sample(x)
```

Timing should therefore live with the future preview/animation consumer or
future animation/track abstraction rather than becoming intrinsic sampling
state on reusable `EasingCurve`.

`ANIMATION-TIMING-01` depends on the future animation-target/track architecture.
Avoid storing both independent authoritative speed and duration values unless a
clear synchronization contract is designed.

#### `BUG-01` — Graph zoom slider and Autofit are not wired

- **Affected components:**
  `addons/easing_curve/easing_curve_editor_inspector_plugin.gd` and
  `addons/easing_curve/scripts/easing_curve_editor.gd`.
- **Category:** concrete integration bug; Inappropriate Intimacy/direct-field
  bypass; missing integration characterization.
- **Evidence:** Inspector construction assigns
  `easing_curve_editor._slider = zoom_slider_container` at line 897. The only
  code that connects `slider_changed` and `autofit_pressed` to
  `_on_slider_changed()` / `_on_autofit_pressed()` is
  `set_slider_container()` at lines 691-699, and repository search finds no
  caller of that method. The gesture suite likewise assigns `_slider` directly
  and calls Autofit methods directly, so its 124 checks do not exercise the
  missing signal path.
- **Why it matters:** dragging/wheeling the slider and pressing Autofit can
  emit from `zoom_slider_container.gd` without changing the graph. Graph-wheel
  zoom takes a separate direct path, which explains why part of zoom behavior
  can still work. This violates the preserved pan/zoom/autofit contract and is
  directly relevant to `VIEW-STATE-01`.
- **Recommended improvement:** route construction through the existing public
  setup method and add an integration characterization that drives the
  container signals/buttons rather than private graph callbacks.
- **Expected payoff / effort / risk:** restores intended controls and removes
  a private-field bypass; low implementation effort and low risk, provided
  initial slider restoration is checked for duplicate notifications.
- **Behavior to protect:** graph-wheel zoom, slider zoom, Autofit reset,
  zoom-around-pointer, stored slider/zoom/pan callbacks, and Inspector rebuild.
- **Sequencing:** resolve before `POINT-NAV-01`, `VIEW-STATE-01`, or
  `PREVIEW-01` so feature validation starts from a working graph toolbar/view
  baseline.

#### `BUG-02` — Update-available notification is debug-gated

- **Affected component:** `addons/easing_curve/scripts/update_checker.gd`.
- **Category:** concrete control-flow bug; dead production behavior; missing
  unit coverage.
- **Evidence:** `DEBUG_UPDATE_CHECKER` is `false` at line 27, while
  `update_available.emit(...)` at lines 205-209 is indented inside
  `if DEBUG_UPDATE_CHECKER:`. A successful newer-version response therefore
  emits no signal in normal builds, so the plugin's connected dialog callback
  cannot run.
- **Why it matters:** the shipped automatic update checker silently cannot
  announce updates despite the enabled setting, menu, request, parsing, ignore
  list, and dialog code.
- **Recommended improvement:** keep only diagnostic printing behind the debug
  flag; emit independently after the ignore check. Add deterministic tests for
  newer/equal/older/malformed/ignored response behavior without live network
  dependence.
- **Expected payoff / effort / risk:** restores a user-visible shipped feature;
  low implementation effort and low-to-medium risk because notification UI is
  visible-editor behavior.
- **Behavior to protect:** disabled setting, ignored versions, single in-flight
  request, semantic version comparison, and non-blocking network failure.
- **Sequencing:** independent of the graph features; complete before release
  if update checking remains shipped and enabled.

#### `BUG-03` — Historical resource-save conversion needs characterization

- **Affected component:**
  `addons/easing_curve/easing_curve_editor_plugin.gd`; related resource
  round-trip and preset-state tests.
- **Category:** suspected obsolete workaround / divergent behavior;
  serialization and editor-lifecycle coverage gap.
- **Evidence:** `_on_resource_saved()` at lines 93-101 unconditionally changes
  every non-custom Bézier transition to `TRANS.CUSTOM` after a save. Current
  runtime tests intentionally preserve a built-in transition across direct
  save/load, and current Inspector logic retains built-in preset identity while
  displaying modified geometry with `*` and a Reset action. No registered test
  invokes the EditorPlugin resource-saved hook, so the two models are not
  reconciled by the 4,908-check baseline.
- **Why it matters:** in a normal editor save, the in-memory resource may lose
  its selected built-in transition/ease identity and preset Reset behavior
  immediately after the file was written. The hook predates the current flat
  point storage and preset-modified model, but it was originally added to
  protect custom geometry, so removing it without characterization is unsafe.
- **Recommended improvement:** first add Editor-host/visible characterization
  for clean and modified built-in presets, external `.tres` and scene-embedded
  resources, dirty state after save, reload, and second save. Then either
  retain the hook as an explicit compatibility decision or narrow/remove it
  with serialization evidence.
- **Expected payoff / effort / risk:** medium payoff, low code effort, but high
  compatibility risk until characterized.
- **Sequencing:** evaluate before `VIEW-STATE-01` changes saved-resource dirty
  behavior; do not change the hook opportunistically.

#### `PERF-01` — Full transformed-width Bézier redraw

- **Affected component:** `addons/easing_curve/scripts/easing_curve_editor.gd`,
  especially `_draw_bezier_curve()` and `_draw_bezier_segment()`.
- **Category:** observable avoidable hot-path work; unmeasured performance
  opportunity.
- **Evidence:** every Bézier segment is passed visible bounds `0.0..1.0` at
  line 1009. `_draw_bezier_segment()` then sets its iteration count from the
  transformed start/end pixel distance. At the supported 10x zoom this can be
  about ten solves per physical horizontal pixel even when most of the curve
  is panned off-screen. Each iteration performs X-to-t root solving and line
  drawing, and graph input queues redraws repeatedly during drag/pan/zoom.
- **Why it matters:** cost grows with zoom, viewport width, and segment count;
  v1.0.9 adds more graph-toolbar/preview activity. No benchmark or visible lag
  was measured during this audit, so this is not presented as a current
  release blocker.
- **Recommended improvement:** if profiling confirms impact, derive visible
  world-X bounds from the clipped view/pan transform and cap/adapt tessellation
  without changing `sample()` semantics or endpoint/vertical-segment drawing.
- **Expected payoff / effort / risk:** potentially large redraw reduction at
  high zoom; medium effort and medium visual-regression risk.
- **Behavior to protect:** curve/sample equivalence, vertical/equal-X segments,
  missing endpoints, overshoot, pan/zoom positioning, and line continuity.
- **Sequencing:** measure after `PREVIEW-01` design or when practical lag is
  observed; otherwise keep deferred.

### 4.2 `TEST-01` — Serialization scratch-directory editor scan race

**Status:** COMPLETE

#### Objective

Eliminate the intermittent editor error
`Cannot change to 'res://test/_serialization_transition_contract/' folder.`
without weakening legacy/current-format serialization coverage.

#### Scope

- move only the generated current-format round-trip directory used by
  `serialization_transition_contract_test.gd` outside the project filesystem;
- retain the two authoritative legacy fixtures under `res://test/presets/`;
- retain `ResourceSaver` / `ResourceLoader.CACHE_MODE_IGNORE` round-trip checks;
- retain cleanup of both generated `.tres` copies and their directory;
- update this tracker with exact validation and closeout results.

#### Non-goals

- no production resource/storage/schema changes;
- no changes to legacy fixtures, the authoritative suite manifest, runner
  semantics, or unrelated temporary test files;
- no attempt to suppress unrelated expected serialization diagnostics.

#### Architecture / risk assessment

The error is an editor filesystem race, not a production serialization defect.
The test creates and removes `res://test/_serialization_transition_contract`;
an already-open editor can discover the directory and then attempt to scan it
after cleanup has removed it. `user://` supports the same Godot
`ResourceSaver`, `ResourceLoader`, `DirAccess`, and globalized-path operations
but is outside the editor's `res://` filesystem scan.

This preserves the compatibility boundary because input fixtures still load

### 4.4 `VIEW-STATE-01` — Persistent EasingCurve graph zoom/pan

**Status:** NOT STARTED

#### Objective

Persist each `EasingCurve` resource's graph zoom and pan across project/editor
restarts.

#### Existing architecture

The resource already owns in-memory per-resource view state:

- `_last_slider_value`;
- `_last_zoom`;
- `_last_pan`.

The Inspector restores that state when rebuilding the curve editor, so
Inspector refresh and resource switching already preserve view state within the
same session.

#### Agreed direction

Preserve `EasingCurve` as the owner and persist the state as private
storage-only resource data rather than presenting zoom/pan as normal public
curve parameters.

#### Important design consequence to review before implementation

Persisting editor view state with the Resource may make panning/zooming mark a
scene/resource dirty and may create source-control diffs even when curve
geometry is unchanged.

This is not automatically a defect; it is a consequence of the requested
resource-persistent model and must be explicitly validated/accepted during the
work-item design review.

#### Compatibility constraints

- existing older resources without the new storage must load successfully;
- missing values default to the existing normal view;
- view state must not affect `sample()` output;
- view state should remain hidden from ordinary runtime-facing Inspector
  parameters;
- no change to zoom formulas, limits, pan semantics, autofit, wheel behavior,
  or zoom-around-pointer unless separately approved.

#### Additional validation

- save resource with non-default zoom/pan;
- restart/reload and verify exact intended restoration;
- external `.tres` and scene-embedded resource behavior where applicable;
- older fixture/resource compatibility;
- resource-dirty/source-control behavior documented;
- Inspector refresh and A -> B -> A resource switching still work;
- autofit returns to the expected default and persists appropriately.

#### Execution plan

Not generated yet. Plan after `AUDIT-01` is reviewed/classified.
