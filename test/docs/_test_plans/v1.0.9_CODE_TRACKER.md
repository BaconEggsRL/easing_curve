# Easing Curve v1.0.9 Code Tracker

## 1. Release Charter [FROZEN]

### 1.1 User-confirmed v1.0.9 goals

The user confirmed the following goals for v1.0.9:

1. **Code-smells / architecture / performance / bug review**
   - identify code smells and architecture improvements for future
     maintainability;
   - identify meaningful speed/performance bottlenecks and worthwhile
     optimizations;
   - identify concrete program bugs discovered during the review;
   - do not assume every finding must be implemented in v1.0.9.

2. **Graph-toolbar point navigation / reordering controls**
   - add graph-toolbar arrows for selecting and/or reordering points;
   - if both navigation and reordering are exposed, keep their semantics
     visibly distinct rather than making one ambiguous arrow operation;
   - reuse existing point ordering, selection, identity, and Undo/Redo
     behavior rather than creating a second ordering model.

3. **Persist graph zoom and pan through project/editor restarts**
   - store graph view state with the `EasingCurve` resource so it survives
     editor/project restarts;
   - preserve the current per-resource ownership model;
   - review serialization/resource-dirty/source-control implications before
     implementation;
   - preferred direction from the accepted feature review is private
     storage-only resource state rather than visible public curve parameters.

4. **Curve-editor playback/sample preview**
   - add a playback bar, playhead, dot, or equivalent preview UI to the curve
     editor;
   - the preview must make the current normalized X value and the corresponding
     `EasingCurve.sample(x)` output visually understandable;
   - keep v1.0.9 preview focused on the easing curve itself rather than
     animating arbitrary scene properties.

## 2. Future Release Roadmap [FROZEN USER-SUPPLIED BOUNDARY]

The user explicitly moved the following features out of v1.0.9. These entries
preserve the agreed direction but are not active authorization.

### 2.1 Future / v1.0.10 — `MULTI-EDIT-01` — Multi-point editing

**Status:** FUTURE / NOT ACTIVE

#### User goal

Support multi-point editing, with Shift-drag potentially acting as a selection
rectangle. Intended batch operations include:

- selecting multiple graph points;
- deleting selected points;
- updating Handle Mode across the selection;
- updating control state/mode across the selection;
- translating selected points together.

#### Agreed release rationale

This should be treated as a dedicated release-level feature rather than folded
into v1.0.9 because current graph/Inspector selection is fundamentally
single-point oriented.

The difficult part is not drawing the selection rectangle; it is introducing a
coherent multi-selection model across:

- graph selection/highlighting;
- Inspector state;
- point Resource identity through reorder;
- batch translation/order/endpoint behavior;
- batch Handle Mode/control-state editing;
- atomic Undo/Redo;
- selection restoration through Undo/Redo and Inspector refresh.

#### Existing architectural reservation

v1.0.8 deliberately leaves pre-held Shift unconsumed by the initial axis-drag
hold. Preserve that reservation unless a later multi-selection design explicitly
changes it.

### 2.2 Future / v1.0.10 or later — `ANIMATION-TARGET-01` — Node/property assignment

**Status:** FUTURE / NOT ACTIVE

#### User goal

Add AnimationPlayer-like assignment of easing behavior to a Node/property, such
as:

- position;
- rotation;
- scale;
- other supported animatable properties.

#### Agreed architectural direction

Do not assume Node/property target metadata belongs directly on `EasingCurve`.
`EasingCurve` should remain the reusable interpolation/geometry resource.

A future design should evaluate a separate track/animation abstraction, for
example conceptually:

```text
EasingCurve
    -> normalized interpolation

Easing animation/track resource
    -> target Node/property
    -> from/to values
    -> timing
    -> EasingCurve reference
```

The exact class/resource/API is not yet frozen and requires its own architecture
review before implementation.

#### Major design questions for that future release

- target path ownership and root-relative semantics;
- node rename/path resilience;
- local versus global transforms;
- supported property types;
- from/to value ownership and absolute/relative modes;
- reusable curves across multiple targets;
- safe editor preview/revert behavior;
- runtime versus editor-only responsibility;
- Undo/Redo behavior;
- external `.tres` resources shared across scenes.

### 2.3 Future / v1.0.10 or later — `ANIMATION-TIMING-01` — Duration / speed

**Status:** FUTURE / NOT ACTIVE

#### User goal

Add speed/duration parameters for animations.

#### Agreed architectural direction

Duration/speed does not transform the easing function in the same way as
`reverse` or `invert` and therefore should not be treated as an `EasingCurve`
Global Transform merely because that Inspector group already exists.

Normalized easing remains conceptually:

```text
elapsed time / duration
    -> normalized x
    -> EasingCurve.sample(x)
```

Timing should therefore live with the future preview/animation consumer or
future animation/track abstraction rather than becoming intrinsic sampling
state on reusable `EasingCurve`.

`ANIMATION-TIMING-01` depends on the future animation-target/track architecture.
Avoid storing both independent authoritative speed and duration values unless a
clear synchronization contract is designed.

#### `BUG-01` — CLOSED: `_slider` assignment does invoke the setter

The original audit incorrectly treated direct assignment to
`easing_curve_editor._slider` as bypassing `set_slider_container()`. Current
`easing_curve_editor.gd` declares `_slider` with `set = set_slider_container`,
so Godot property assignment invokes that setter. Codex also confirmed this with
a targeted runtime probe: assigning `_slider` created the expected signal
connections and slider signals changed the graph zoom state.

Retain this only as a minor encapsulation/readability note: calling
`set_slider_container()` explicitly would make intent clearer and reduce private
field coupling, but there is no broken slider/Autofit behavior to fix. Close the
P0 classification and do not spend a release work item on it without new
behavioral evidence.

#### `BUG-02` — CLOSED: update notification debug gate

Current `update_checker.gd` emits `update_available` after the ignored-version
check regardless of `DEBUG_UPDATE_CHECKER`; only logging remains debug-gated.
This finding stays closed.

#### `BUG-03` — P1: post-save mutation changes resource identity

`plugin.gd::_on_resource_saved()` still changes any saved non-custom Bézier
`EasingCurve` to `TRANS.CUSTOM` *after* save. That behavior now conflicts with
the established model in which modified built-in geometry retains its selected
transition/ease origin and exposes modified/reset state.

Characterize external `.tres` and scene-embedded resources across clean preset,
modified preset, first save, in-memory state after save, second save, and
reload. Do not simply delete the hook without that evidence because it is
historical compatibility code. If characterization confirms the current
preset-origin model is authoritative, narrow/remove the hook and preserve custom
geometry by the current flat point serialization path instead.

#### `TEST-03` — P1: passing suite can contain unexpected engine errors

`test/runners/run_all_tests.ps1` currently considers a suite passing when it has
exit code 0, a `PASS:` marker, no timeout, and no `SCRIPT ERROR:`. It does not
reject or classify other `ERROR:` diagnostics. Existing runs can therefore be
green while printing RID/ObjectDB leaks, certificate-store failures, intentional
negative-path errors, or a genuinely new engine/plugin error.

Do **not** change this to a blanket `ERROR:` failure rule because several known
messages are intentional or environment-specific. Add explicit expected
patterns/allowlists (preferably suite/mode scoped), preserve unknown diagnostics
with failed-run artifacts, and consider a clean-project gate containing only
`addons/easing_curve` to remove unrelated Godot-AI plugin noise.

#### `ARCH-01` — CLOSED: point-state transition authority already extracted

Codex's duplication concern described an older state. Current code already has
`easing_curve_point_state.gd` as a value carrier and
`easing_curve_point_state_transition.gd` as the pure transition authority.
`point.gd` delegates live setter semantics to it, while
`easing_curve_point_snapshot_mutator.gd` adapts snapshot data and delegates
Inspector semantics to the same component. This directly addresses the earlier
Duplicate Code / Shotgun Surgery risk. Keep the dictionary snapshot format as
the serialization compatibility boundary and do not re-split this state machine.

#### `ARCH-02` / `ARCH-03` — future maintainability extractions

The remaining highest-value architectural smells are the two coordinators that
change for many unrelated reasons:

- `easing_curve.gd`: runtime sampling, transition/preset generation, dynamic
  serialization, point topology/notifications, editor snapshots/transactions,
  and per-resource editor view state. Treat as **Large Class** and **Divergent
  Change**. Keep `EasingCurve` as the public façade and extract, in order of
  safety/payoff: preset/transition geometry factory; serialization/snapshot
  codec; then editor-only transaction/view-state support.
- `easing_curve_editor_inspector_plugin.gd`: Inspector construction, bindings,
  point-list editing, selection synchronization, clipboard, graph/Inspector
  transactions, reorder, and Undo/Redo coordination. Treat as **Large Class**,
  **Divergent Change**, and localized **Inappropriate Intimacy**. Extract small
  point-list, clipboard, and transaction controllers behind the existing
  Inspector plugin rather than rewriting the editor layer.

Avoid a one-shot architecture rewrite. Extract one responsibility only when its

remain supported. Earlier measurement showed this permanent synchronization

main obvious scaling floor left in the Bézier hot path.

methods with revisioning, or a batch-sampling API that performs synchronization

thousands of samples per frame; ordinary 2-3 point curves are not urgent.

### 4.3A `TEST-03` — Unexpected diagnostic gate for automated suites

**Status:** PLANNING COMPLETE — AWAITING APPROVAL

#### Objective

Strengthen the authoritative test runner so a suite cannot remain green when it
emits a previously unclassified Godot `ERROR:` or `WARNING:`, while preserving
known intentional negative-path diagnostics and known headless Editor shutdown
noise.

The goal is diagnostic classification, not diagnostic suppression.

#### Scope

- modify only the authoritative PowerShell runner unless implementation proves a
  small runner-local helper is justified;
- inspect top-level Godot diagnostics from the already-captured suite output;
- keep `SCRIPT ERROR:` unconditionally fatal;
- permit only explicitly classified diagnostics, scoped by execution mode and/or
  suite where appropriate;
- fail the suite when any unclassified top-level `ERROR:` or `WARNING:` appears;
- preserve failed-suite artifacts through the runner's existing failed-result
  retention path;
- report allowed/unexpected diagnostic counts in the test summary so a green run
  remains transparent rather than silently discarding noise.

#### Non-goals

- do not suppress or hide Godot output;
- do not make every textual occurrence of `error` a failure (for example,
  `tween_equivalence_test.gd` legitimately prints `max_error=...` metrics);
- do not change production/plugin code;
- do not rewrite the Editor-host test harness merely to eliminate Godot shutdown
  diagnostics;
- do not create a separate clean-copy project as part of this bounded item;
- do not blanket-allow arbitrary Editor-host errors.

#### Investigation baseline — 2026-09-01

A fresh diagnostic probe ran the same 18 registered suite entrypoints on Godot
4.7.1 through `test/runners/run_godot.ps1`, with isolated AppData and the same
headless versus Editor-host modes used by the authoritative runner. Every suite
returned exit 0, printed its PASS marker, and contained no `SCRIPT ERROR:`.

Top-level diagnostics were defined narrowly as lines beginning with
`SCRIPT ERROR:`, `ERROR:`, or `WARNING:`. This avoids false positives from
normal metric text such as `max_error=`.

Observed diagnostic classes:

- seven of the eight headless suites emitted **zero** top-level diagnostics;
- `serialization_transition_contract_test.gd` emitted exactly three intentional
  negative-path `ERROR:` messages for malformed/missing snapshot lifecycle and
  an unknown point property; these are part of its passing contract checks;
- all ten Editor-host suites emitted nine known shutdown diagnostics apiece;
  the common families are headless-editor scan abort, Canvas/CanvasItem RID
  leaks, ObjectDB exit leaks, and native RID-allocation exit leaks;
- `easing_curve_editor_gesture_characterization_test.gd` replaces the normal
  scan-abort line with its existing `resources still in use at exit` shutdown
  diagnostic and uses higher allocation counts, but does not introduce a new
  in-test failure;
- certificate-store and editor-settings errors documented in older audit runs
  did **not** recur in this fresh probe and therefore should not be preemptively
  allowlisted.

Across the current suite this produces **93 unique expected top-level diagnostic
lines by suite**: 3 suite-specific intentional errors plus 9 shutdown diagnostics
for each of 10 Editor-host suites.

A temporary PowerShell classifier prototype using the proposed rules reported:

```text
allowed=93
unexpected=0
sentinel_detected=True
```

The sentinel check used an injected `ERROR: TEST03 unexpected sentinel` against a
clean headless suite and verified that the proposed default is fail-closed.

#### Root cause / current runner weakness

`test/runners/run_all_tests.ps1` currently determines pass/fail from:

- no timeout;
- Godot exit code 0;
- a `PASS:` marker in stdout/stderr;
- absence of `SCRIPT ERROR:`.

It captures `stdout.txt`, `stderr.txt`, and `godot.log`, but its semantic pass
check only searches the concatenated stdout/stderr for `SCRIPT ERROR:`. Generic
Godot `ERROR:` and `WARNING:` lines therefore have no effect on `$passed`.
Because passing suite directories are deleted immediately, a genuinely new
non-script engine/plugin diagnostic can be lost after a green run unless someone
noticed it in console output.

#### Recommended design

Keep the change runner-local and fail-closed:

1. Extract only top-level severity lines beginning with `SCRIPT ERROR:`,
   `ERROR:`, or `WARNING:` from stdout, stderr, and the existing Godot log;
   trim and de-duplicate them per suite.
2. Treat every `SCRIPT ERROR:` as fatal regardless of any allowlist.
3. Define a small common **Editor-host shutdown** allowlist for the established
   shutdown families only: scan abort, Canvas/CanvasItem RID leaks, ObjectDB exit
   leaks, and native RID-allocation exit leaks. Match variable counts but do not
   suppress the lines.
4. Define suite-specific exact allowlists for:
   - the three intentional serialization lifecycle/unknown-property errors;
   - the gesture suite's existing `resources still in use at exit` shutdown
     message.
5. Any top-level diagnostic that matches neither the applicable common patterns
   nor the suite-specific patterns makes the suite fail.
6. Add allowed/unexpected diagnostic counts to `$results`. When unexpected
   diagnostics exist, print them explicitly. Existing `$passed == false`
   cleanup behavior will then preserve that suite's stdout/stderr/log/AppData
   automatically for investigation.
7. Keep the existing PASS marker, timeout, exit-code, and `SCRIPT ERROR:` gates;
   this is an additional gate rather than a replacement.

Do not encode the current numeric leak counts as requirements: they vary across
Editor fixtures and can change with engine internals. Conversely, keep the
allowlist restricted to known diagnostic *families* and suite-specific messages
so a new unrelated `ERROR:`/`WARNING:` still fails.

#### Architecture / risk assessment

This is a test-infrastructure-only change with low production risk and moderate
runner risk. The primary failure mode is an allowlist that is either too broad
(masking regressions) or too brittle (failing harmless engine-version changes).
Mode-scoped families plus exact suite-specific intentional messages provide the
best current balance.

Reading `godot.log` as well as stdout/stderr is worthwhile because the runner
already creates it and it is the chronological Godot log; de-duplication avoids
counting messages echoed to multiple streams. The raw output should remain
visible so allowed diagnostics are still inspectable.

### 4.5 `VIEW-STATE-01` — Persistent EasingCurve graph zoom/pan

**Status:** NOT STARTED

#### Objective

Persist each `EasingCurve` resource's graph zoom and pan across project/editor
restarts.

#### Existing architecture

The resource already owns in-memory per-resource view state:

- `_last_slider_value`;
- `_last_zoom`;
- `_last_pan`.

The Inspector restores that state when rebuilding the curve editor, so
Inspector refresh and resource switching already preserve view state within the
same session.

**Current-state verification — 2026-08-31:** these three fields are still plain
private variables and are not included as storage properties by
`_get_property_list()`. They therefore remain session-memory state only; the
requested restart persistence has not been implemented.

#### Agreed direction

Preserve `EasingCurve` as the owner and persist the state as private
storage-only resource data rather than presenting zoom/pan as normal public
curve parameters.

#### Important design consequence to review before implementation

Persisting editor view state with the Resource may make panning/zooming mark a
scene/resource dirty and may create source-control diffs even when curve
geometry is unchanged.

This is not automatically a defect; it is a consequence of the requested
resource-persistent model and must be explicitly validated/accepted during the
work-item design review.

#### Compatibility constraints

- existing older resources without the new storage must load successfully;
- missing values default to the existing normal view;
- view state must not affect `sample()` output;
- view state should remain hidden from ordinary runtime-facing Inspector
  parameters;
- no change to zoom formulas, limits, pan semantics, autofit, wheel behavior,
  or zoom-around-pointer unless separately approved.

#### Additional validation

- save resource with non-default zoom/pan;
- restart/reload and verify exact intended restoration;
- external `.tres` and scene-embedded resource behavior where applicable;
- older fixture/resource compatibility;
- resource-dirty/source-control behavior documented;
- Inspector refresh and A -> B -> A resource switching still work;
- autofit returns to the expected default and persists appropriately.

#### Execution plan

Not generated yet. Plan after `AUDIT-01` is reviewed/classified.
