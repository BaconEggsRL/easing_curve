## 3. Compatibility constraints

The following observed behavior is a v1.0.7 preservation contract.

### Stored point data and enum values

- `EasingCurvePoint` exports `position`, `left_control_point`,
  `right_control_point`, and `handle_mode`; it stores hidden
  `left_force_linear`, `right_force_linear`, and `locked` properties.
- `EasingCurve.POINT_PROPERTIES` fixes the serialized dynamic property set and
  order: `position`, `left_control_point`, `right_control_point`, `locked`,
  `handle_mode`, `left_force_linear`, `right_force_linear`
  (`scripts/easing_curve.gd:189-197`). Storage paths remain
  `_point_<index>/<property>`, preceded by `_point_count`.
- The lock dictionary schema remains exactly `position`,
  `left_control_point`, and `right_control_point`, each boolean. Storage
  loading normalizes that exact schema (`scripts/easing_curve.gd:759-765`).
- `HandleMode` numeric values remain Free=0, Linear=1, Balanced=2,
  Mirrored=3, Linked=4. `ControlSide` remains Left=0, Right=1;
  `ControlState` remains Free=0, Linear=1, Locked=2. `CurveMode` remains
  Bezier=0, Function=1; `EASE` remains In=0, Out=1, InOut=2, OutIn=3; and
  `TRANS` retains its present declaration order/value sequence Custom=0 through
  CSSCubicBezier=21 (`scripts/easing_curve.gd:13-40`).

### Snapshots and restoration

- A point snapshot is resource-free and has exactly `positions`,
  `left_control_points`, `right_control_points`, `handle_modes`, `locks`,
  `left_force_linear`, and `right_force_linear` (`scripts/easing_curve.gd:1200-1236`).
  Its vector collections and enum/state collections retain their current Packed
  array types.
- A complete editor-state snapshot has `ease_type`, `trans_type`,
  `curve_mode`, `from_start`, `reverse`, `invert`,
  `bezier_parameter_snapshot`, `point_snapshot`, and `function_snapshot`
  (`scripts/easing_curve.gd:1510-1521`). `point_resource_ids` is an
  editor-only restoration payload accepted when present, not part of the
  normal captured editor-state dictionary.
- Snapshot restoration clears Force Linear, temporarily selects Free mode,
  restores position/controls/mode, restores Force Linear without geometry
  modification, then normalizes locks. That order is required
  (`scripts/easing_curve.gd:1465-1507`).

### Point interaction, ordering, and selection

- Linear collapses both handles to the point. Leaving Linear creates default
  horizontal handles of length 0.1. Balanced mirrors direction while retaining
  individual lengths; Mirrored matches direction and length; Linked aliases the
  two control values. Existing point-state characterization tests define the
  exact transition behavior.
- Locks apply to position always; handle locks are active only in Free/Linked.
  A Linear handle's Inspector editability follows its raw lock value. Force
  Linear is supported only in Free/Linked; it collapses the affected handle(s)
  to position. In Linked, either force flag forces both handles. Lock wins over
  Force Linear and locking a formerly forced handle restores its default 0.1
  handle before locking. These are current behavior, not redesign targets.
- Points remain ordered by x for operations that build/sort the curve. Adding a
  point uses endpoint-takeover ordering; removing and setting points preserve
  the existing topology/notification semantics. Position-x edits can reorder
  the same Resources. Endpoints and their current takeover behavior remain
  unchanged.
- Logical selection is point Resource identity plus selected property, not only
  a visible list index. It must survive Inspector reconstruction, graph/list
  synchronization, add/remove/reorder, and Undo/Redo; restored ordering uses
  point instance IDs before restoring primitive point data
  (`scripts/easing_curve.gd:1531-1566`).

### Notifications, Undo/Redo, and sampling

- Point changes connect to `EasingCurve._on_point_changed`, which synchronizes
  point connections then publishes one curve change with point data changed and
  no property-list refresh (`scripts/easing_curve.gd:2454-2458`).
- `_notify_curve_changed` increments the revision, optionally refreshes the
  property list, emits `points_changed(_points)` only for point-data changes,
  then emits Resource `changed` (`scripts/easing_curve.gd:1936-1942`).
  Continuous snapshot edits defer notification until completion; parameter edit
  nesting preserves its current deferred/coalesced timing.
- Editor actions use complete editor-state snapshots and one Undo/Redo action.
  Reorders additionally restore Resource ordering, Inspector notification, and
  selection payloads through `EasingCurveEditorUndo`; initial edits are already
  applied and commits use `commit_action(false)`.
- Sampling clamps the public offset to [0, 1]. Function mode initializes/calls
  its callable and applies reverse/invert at sample time; Bezier mode samples
  existing geometry without applying those transforms again. Fewer than two
  points return 0.0. Segment controls clamp to endpoint x bounds and overlap is
  resolved to a shared x (`scripts/easing_curve.gd:2038-2166`).
- Transition/function mapping, parameter visibility/defaults, generated
  function snapshots, easing availability, and callable behavior remain as
  exercised by the serialization/transition and tween-equivalence suites.
  Constant and Back parameter notification behavior remains revision-gated.

## 4. Current architecture summary

`EasingCurvePoint` owns point geometry, handle-mode geometry transforms, lock
and Force Linear state, and a static weak-reference map of Inspector Vector2
input Controls. `EasingCurve` owns the point list, dynamic serialized storage,
point/resource signal lifecycle, snapshots, runtime sampling, transitions, and
notification/revision behavior. `EasingCurveEditor` owns graph interaction and
renders points/handles; `easing_curve_editor_inspector_plugin.gd` owns Points
list controls, Inspector selection, copy/paste, default/reset controls, and
action assembly. `EasingCurveEditorUndo` applies the standard editor-state
snapshot protocol.

The `EasingCurvePoint._input_controls` bridge is deliberately editor-specific
state held by a Resource: point setters synchronously update Inspector numeric
inputs and their read-only state. This makes property mutation behavior depend
on Controls keyed by property-name plus axis, despite those Controls not being
serialized.

## 5. Points-property dependency/coupling matrix

| Concern | `position` | `left_control_point` / `right_control_point` | `handle_mode` | locks / Force Linear |
| --- | --- | --- | --- | --- |
| Domain ownership | Point setter moves unlocked controls; curve uses position for ordering/sampling. | Point setter computes both controls under mode rules; curve samples them. | Point owns enum and geometry conversion. | Point owns hidden bools/dictionary and editability. |
| Serialization | Dynamic storage property, Vector2 default assumption. | Same dynamic Vector2 paths. | Explicit dynamic INT special case. | `locked` explicit Dictionary; each Force Linear field explicit BOOL. |
| Snapshot | `positions`. | Separate left/right PackedVector2 keys. | `handle_modes` PackedInt32 key. | `locks` plus separate PackedByteArray keys. |
| Inspector | Custom Vector2 header/inputs/reset/path selection. | Same widgets with left/right branches. | Dedicated option widget and toolbar option. | Lock buttons/dictionary actions and Force Linear controls. |
| Graph | Point drag, hit test, x-order preview/reorder. | Handle drag/hit test/drawing. | Determines toolbar/control-state display and draw/edit behavior. | Changes input read-only state and handle display/editability. |
| Undo/Redo/tests | Snapshot/selection/order actions; drag and reorder tests. | Snapshot/gesture/alias tests. | Point-state and editor Undo tests. | Control editability, Force Linear persistence, point-state, and Undo tests. |

Concrete coupling requiring property knowledge today:

- `POINT_PROPERTIES`, `_get_property_list`, and `_set` in
  `scripts/easing_curve.gd:189-197,657-768` enumerate every stored property,
  branch to choose only four types, and normalize the lock schema by name. The
  default type is `TYPE_VECTOR2`; adding a non-Vector2 point option requires a
  new exception.
- `make_point_snapshot`, snapshot comparison, transforms, and
  `_restore_point_snapshot_state` use separate typed arrays and explicit
  left/right/lock/Force Linear branches. Every point option must be added to
  capture, comparison, restore, and any reverse/invert behavior.
- `EasingCurvePoint` has name checks in `_set`, `is_lock_active`,
  `is_position_input_editable`, `_update_control_point_inputs`, input-control
  lookup keys, and lock-update loops. It assumes the editable point properties
  are the three Vector2 names and maps every non-position input to Right.
- `easing_curve_editor_inspector_plugin.gd` has custom header creation,
  property-path copy/paste validation, Vector2 value handling, default/reset
  selection, action naming, and snapshot mutation branches. It contains direct
  left/right mappings for lock-to-Force-Linear, control array name, default
  offset, and Linked behavior (notably around lines 3041-3119 and 3142-3157).
- `scripts/easing_curve_editor.gd` carries separate graph controls for point,
  left handle, right handle, toolbar handle mode, and left/right control state;
  its signal carries a property name and Variant, but downstream logic remains
  name-based.
- Tests are deliberately property-aware: serialization asserts storage and
  snapshot schemas; point-state/editability/linear-alias tests encode
  mode/lock/Force Linear rules; graph/list/reorder/selection/Undo suites assert
  selection and action behavior. New point options require focused contracts
  across these suites, rather than a single property declaration.

## 6. Initial refactor goals

The later v1.0.7 work may reduce the number of independent property lists and
name/type branches required to add a point option such as `handle_mode`, while
preserving every constraint above. It should establish one authoritative
description of point-property storage, snapshot, defaults, editability,
Inspector presentation, and applicable graph behavior; separate generic
property flow from intentional geometry-specific behavior; and retain current
serialized names, enum values, snapshots, selection identity, signals, and
Undo/Redo boundaries.

No implementation approach, registry, abstraction, production move, public API
rename, serialized-format change, enum change, or test change is authorized by
this Step 1 document.

## Final architecture summary

Before v1.0.7, adding a point option could require repeating the same property
knowledge in serialized storage, type/default handling, Inspector eligibility,
normal row construction, live input synchronization, and snapshot lifecycle
code. A small addition could therefore miss an unrelated subsystem.

`EasingCurve.POINT_PROPERTY_DEFINITIONS` is now the authoritative passive
metadata source for the concerns it owns: name, Variant/storage type, default,
Inspector visibility, reset and copy/paste eligibility, Inspector label, editor
kind, snapshot key, and opt-in ordinary snapshot lifecycle participation. It
contains no Controls, Callables, geometry/mutation/Undo logic, or transform and
restoration callbacks. Dynamic `_point_<index>/<property>` storage derives its
property type from this descriptor rather than assuming Vector2 fields with
exceptions.

The Inspector uses descriptor metadata for eligibility and shared normal-row
chrome, while preserving a separate intentional presentation order: Position,
Handle Mode, applicable Left Control, then applicable Right Control. Serialized
descriptor order and visible Inspector order are separate compatibility concerns.
The Inspector now owns weak Vector2 bindings and observes `EasingCurvePoint.changed`;
point Resources no longer know Inspector Controls exist.

Point descriptors map declaratively to the unchanged typed snapshot keys. Typed
snapshot access helpers preserve the existing PackedArray schema. A future
ordinary descriptor-backed property can opt into typed capture, comparison,
restoration, and point-order reversal without independent lifecycle branches.
Existing semantic properties intentionally remain explicit for Position movement
and ordering, left/right geometry, handle-mode transitions, locks, Force Linear,
reverse side swapping, restore ordering, graph interaction, selection/resource

| --- | --- | --- |

```text
EasingCurvePoint: point state + geometry semantics
        ↓
EasingCurve: descriptor + serialization + typed snapshots + sampling
        ↓
Editor/Inspector: presentation + rows + live bindings + edit transactions
        ↓
EasingCurveEditorUndo: editor-state Undo/Redo restoration
```

For a future ordinary property, add domain state, one descriptor entry, an editor
kind only when the UI type is new, intentional presentation placement when
visible, and focused tests. It should not need new storage-type, row-chrome,
live-binding, snapshot-key, snapshot-lifecycle, or Undo/Redo transaction
plumbing. Geometry-affecting properties appropriately require additional
explicit semantic work.

**The point-property extensibility architecture is frozen at the end of this
milestone.** Do not generalize it further unless a concrete future property
exposes a real duplicated responsibility.
