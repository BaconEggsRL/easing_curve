# 5. Important project-wide notes discovered during execution

## 5.1 The v1.0.7 architecture is sufficient for axis constraints

The audit concluded that no gesture-framework refactor is required before axis-constrained dragging.

The existing graph flow already provides the required boundary:

```text
_handle_left_pressed()
    -> establishes selected point/control and drag state

_handle_drag_motion()
    -> converts view position to world target
    -> checks locks
    -> requests point/control mutation

_handle_left_released()
    -> closes one edit transaction and commits final ordering
```

Axis selection should be applied locally between world-target calculation and the existing clamp/mutation request.

Do not move Inspector snapshot ownership, point-domain Handle Mode behavior, or Undo/Redo transaction boundaries as part of the axis feature.

## 5.2 Do not reopen intentionally preserved architecture

The v1.0.8 audit explicitly says to leave the following alone unless a separate compatibility decision or new evidence justifies change:

- primitive point/function/editor snapshot formats and restore ordering;
- `EasingCurve` ownership of topology, persistence, notifications, and public orchestration;
- distinct runtime point setters versus Inspector snapshot mutation policy;
- built-in Bézier preset generation ownership;
- per-resource graph view-state ownership;
- Godot Editor/deferred/focus/drag workarounds;
- public easing-library surfaces in `easing.gd`;
- explicit test manifest and simple per-suite assertions.

Future agents should not treat these as unfinished refactor tasks merely because they appear structurally large or duplicated.

## 5.3 Public unreferenced symbols are not dead code by default

CLEANUP-01 was explicitly limited to private/reference-proven remnants.

Do not remove public classes, constants, methods, properties, signals, or easing-library surfaces solely because repository search finds no internal caller.

## 5.4 Test execution modes remain explicit

The runner manifest must remain the authority for headless versus Editor-host execution.

Do not introduce automatic test discovery that infers mode from filenames.

## 6.2 Axis-constrained dragging

**Status:** NOT STARTED

### Goal

Add modifier-based axis-constrained dragging for:

- graph points;
- left Bézier control handles;
- right Bézier control handles.

### Architecture constraint

Implement against the existing `_handle_drag_motion()` coordinate path.

Do not use the feature as justification for:

- `EDITOR-01`;
- `EDITOR-02`;
- `EDITOR-03` unless a visual cue is actually needed;
- Undo framework changes;
- snapshot redesign;
- notification-policy changes.

### Product interaction decision still required

Before implementation, choose:

1. modifier key;
2. constraint model.

Current recommended model from planning discussions:

- hold a modifier while dragging;
- determine horizontal versus vertical from dominant **total displacement from the stable drag origin**;
- use a small threshold before locking an axis;
- do not choose axis from latest-frame delta;
- once selected, keep the constraint stable during that modifier hold;
- pressing/releasing the modifier mid-drag must not make the dragged point/control jump;
- releasing the modifier returns smoothly to ordinary 2D dragging.

`Ctrl` is currently the preferred candidate unless repository/Godot interaction inspection shows a conflict.

### Required feature coverage

Add graph characterization covering at minimum:

- unchanged unconstrained point dragging;
- unchanged unconstrained left/right handle dragging;
- horizontal point constraint;
- vertical point constraint;
- horizontal handle constraint;
- vertical handle constraint;
- modifier held before drag;
- modifier pressed during drag;
- modifier released during drag;
- modifier released at gesture completion;
- stable dominant-axis choice near threshold, if dominant-axis design is selected;
- correctness under pan and zoom;
- X endpoint/Y range clamping;
- point-order crossing and endpoint takeover under horizontal constraint;
- no order change under vertical constraint;
- position/control locks;
- Force Linear;
- Free;
- Linear fallback;
- Balanced;
- Mirrored;
- Linked;
- one Undo action per completed drag;
- no Undo action for no-op drag;
- selection/resource identity across Undo/Redo;
- unchanged right-delete;
- unchanged pending-add;
- unchanged pan;
- unchanged wheel zoom;
