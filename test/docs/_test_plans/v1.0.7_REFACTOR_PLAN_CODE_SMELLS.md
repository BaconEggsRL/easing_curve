# 1. P0 — Point behavior exists in two places

This is the smell I would address **first**.

`EasingCurvePoint` already owns the actual point invariants:

* moving a point and moving unlocked controls with it;
* Free/Linear/Balanced/Mirrored/Linked behavior;
* Force Linear;
* locking;
* default handle restoration;
* linked-handle behavior.

But the Inspector independently implements much of the same state machine against primitive snapshots.

For example, `_apply_point_property_change()` independently knows that moving a point must calculate a delta and move each unlocked control. It also contains separate branches for handle modes, control states, Force Linear and locks.

Then `_set_snapshot_handle_mode()` and `_set_snapshot_control_state()` reproduce rules such as:

* Linked makes left/right state shared;
* Force Linear collapses handles;
* leaving Force Linear creates a `DEFAULT_HANDLE_LENGTH` handle;
* Lock overrides Force Linear;
* Linked handles need special restoration behavior.

That means a future change to what, say, **Linked + Force Linear + Lock** means can require modifying both `point.gd` and Inspector snapshot code.

This is simultaneously:

**Feature Envy:** Inspector methods are doing point-domain work.

**Inappropriate Intimacy:** Inspector knows detailed internal invariants of `EasingCurvePoint`.

**Duplicate Code:** the same behavioral rules exist in two implementations.

**Shotgun Surgery:** changing one invariant can require synchronized changes in both places.

The repository's existing refactor plan actually identifies this exact risk as its first major maintenance issue.

### Recommended fix

I would **not** make the Inspector mutate live `EasingCurvePoint`s directly; your primitive snapshot architecture exists for good Godot/live-debug reasons.

Instead introduce one domain-level snapshot mutator, conceptually:

```text
EasingCurvePointSnapshotOps
    set_position(...)
    set_control_point(...)
    set_handle_mode(...)
    set_control_state(...)
    set_locked(...)
    set_force_linear(...)
```

It operates on the primitive point snapshot but owns the same rules as `EasingCurvePoint`.

Even better, where practical, have the point and snapshot implementation share **pure geometry calculations** instead of duplicating them.

Then:

```text
Inspector
    -> asks PointSnapshotOps for changed snapshot
    -> EasingCurve.set_point_snapshot()
```

The Inspector should know **what action the user requested**, not how Linked/Lock/Force Linear interact.

That is the single refactor I expect to pay the largest reliability dividend.

# 2. P0 — Adding a transition is still Shotgun Surgery

There is substantial transition knowledge spread across the codebase.

Within `EasingCurve` alone you currently have:

* `TRANS`
* `FUNCTION_TRANSITIONS`
* `FUNCTION_CLASSES`
* `BEZIER_PARAMETERS`
* `FUNCTION_PARAMETERS`
* `NON_DEFERRED_FUNCTION_PARAMETERS`
* `GENERATED_FUNCTION_TRANSITIONS`
* `FUNCTION_EDITOR_PROPERTIES`

plus exported parameter definitions/defaults.

There is then another independent transition registry in the Inspector:

```gdscript
const TRANSITION_PRESENTATION := [
    ...
    {"transition": EasingCurve.TRANS.PHYSICS_SPRING, "supports_ease": true},
    ...
]
```

which controls grouping and whether Ease is available.

And runtime implementation dispatch happens elsewhere in `_init_function()` and the large `_update_preset()` match.

So adding a transition potentially means touching:

```text
TRANS enum
    ↓
runtime transition metadata
    ↓
parameters / exports / defaults
    ↓
function implementation or Bézier builder
    ↓
function initialization / arguments
    ↓
Inspector presentation
    ↓
Ease eligibility
    ↓
snapshot/reset handling
    ↓
tests
```

That is almost exactly Refactoring.Guru's definition of **Shotgun Surgery**: one conceptual modification creates many small modifications in multiple places. ([Refactoring Guru][2])

Again, your existing refactor plan independently calls this out: adding a transition/parameter requires coordinated edits across enums, metadata, exports, initialization, arguments, preset generation, Inspector presentation, defaults, snapshots and tests.

### Recommended fix

Consolidate **runtime transition metadata**, without putting editor UI concerns into the runtime resource.

For example:

```gdscript
TRANSITION_DEFINITIONS = {
    TRANS.SPRING: {
        "mode": CurveMode.FUNCTION,
        "class": EASING_LIBRARY.Spring,
        "extended": true,
        "parameters": [&"frequency", &"decay"],
        "supports_ease": true,
    },
    ...
}
```

Then derive:

* `is_function_transition()`
* function parameters
* extended callable selection
* Ease support
* maybe generated-data behavior

from that registry.

I'd leave only genuinely presentation-specific information in the Inspector:

```text
category
display order
possibly custom label
```

So the runtime layer doesn't start depending on Inspector concepts.

A regression test should assert that **every `TRANS` enum value has exactly one valid runtime definition**, and every user-visible transition has one Inspector presentation entry.

# 3. P1 — Inspector plugin is genuinely a Large Class

The Inspector script is currently about **102 KB**. By comparison, the actual plugin lifecycle script is ~5.6 KB.

Size alone isn't enough to call something a smell, but the responsibilities make this one clear.

The same script contains:

* `EditorInspectorPlugin` implementation;
* transition dropdown/presentation;
* clipboard handling;
* property context menus;
* point-property selection;
* reset-button layout;
* native property wrapping;
* deferred parameter edit transactions;
* Generate button property;
* custom Points property;
* Points-list drag/drop;
* drag teardown/quarantine handling;
* foldable section implementation;
* point list creation;
* point input creation;
* lock controls;
* Force Linear controls;
* handle mode UI;
* selection persistence;
* point reorder preview;
* Undo/Redo orchestration;
* graph-editor construction and signal wiring.

It even embeds several essentially independent UI classes inside itself, including `DeferredParameterEditorProperty`, `GenerateFunctionEditorProperty`, `PointsEditorProperty`, `PointsListContainer`, and `PointsFoldableSection`.

This satisfies Large Class much more convincingly than simply saying "the file has many lines." Refactoring.Guru defines it as a class accumulating many fields, methods and lines. ([Refactoring Guru][1])

### I would revisit the existing refactor decision here

The repo's refactor plan says:

> Milestone 9 concluded that no Inspector class/file extraction was warranted.

I don't think a **large controller rewrite** is warranted, but I think the current source now provides a very good case for extracting the **leaf UI types**.

Low-risk extractions:

```text
inspector/
    deferred_parameter_editor_property.gd
    generate_function_editor_property.gd
    points_editor_property.gd
    points_list_container.gd
    points_foldable_section.gd
```

None needs a public `class_name`.

The main Inspector remains the coordinator.

That would cut substantial noise without disturbing its sensitive selection/Undo/property-parsing lifecycle.

I would **not yet extract the central point-edit transaction controller** until item #1 above has centralized the point-domain rules.

# 4. P1 — `EasingCurve` is both a Large Class and a Divergent Change hotspot

`easing_curve.gd` is about **86 KB**.

More importantly, `EasingCurve` changes for a lot of unrelated reasons.

It currently owns:

**Domain/runtime**

* transitions;
* parameters;
* sampling;
* Bézier solving;
* function dispatch;
* preset construction;
* generated functions;
* global transformations.

**Point model**

* topology;
* ordering;
* endpoint takeover;
* signal connections.

**Persistence**

* dynamic `_get_property_list()`;
* primitive point storage;
* `_get()` / `_set()`;
* point snapshots;
* function snapshots;
* complete editor-state snapshots.

**Editor coordination**

* edit depth;
* notification suppression;
* pending transaction flags;
* `_applying_editor_state_snapshot`;
* `_last_slider_value`;
* `_last_zoom`;
* `_last_pan`.

It even has explicit curve-editor callbacks:

```gdscript
_on_curve_editor_slider_value_changed()
_on_curve_editor_zoom_changed()
_on_curve_editor_pan_changed()
```

inside the runtime resource.

That is a good example of **Divergent Change**: the same class gets modified for fundamentally different kinds of changes. Refactoring.Guru defines this as having to modify many unrelated methods within one class for different responsibilities. ([Refactoring Guru][2])

### But don't split it in half

The serialization/snapshot machinery is compatibility-sensitive and has accumulated for legitimate Godot reasons. I would leave that intact initially.

The safest extraction is the **pure algorithmic code**:

```text
easing_curve.gd
    public Resource/API/state

bezier_solver.gd
    effective segment controls
    root finding
    Newton fallback
    binary search
    Bézier interpolation/derivative
```

The solver at the end of `easing_curve.gd` is almost entirely pure/static already, which makes this a much safer class extraction than moving serialization or notification state.

Afterward, `preset_factory.gd` is another possible extraction, but I would first see how much the transition registry refactor simplifies `_update_preset()`.

# 5. P1 — `EasingCurveEditor._gui_input()` is a textbook Long Method

This is probably the clearest individual Bloater.

`_gui_input()` handles:

* panning start/stop;
* pan motion;
* pending-point movement;
* point dragging;
* handle dragging;
* locks;
* Force Linear behavior;
* hover resolution;
* cursor selection;
* wheel zoom;
* left-click selection;
* left-click dragging;
* new-point creation;
* right-click deletion;
* deletion dragging;
* releases/gesture boundaries.

All in one event method.

That creates an ordering problem: a change to one gesture can accidentally alter which later branches execute.

I would extract by event/gesture, not by arbitrary line count:

```gdscript
func _gui_input(event):
    if _handle_pan_input(event):
        return
    if event is InputEventMouseMotion:
        _handle_mouse_motion(event)
        return
    if event is InputEventMouseButton:
        _handle_mouse_button(event)
```

with further helpers such as:

```text
_handle_drag_motion()
_update_hover()
_handle_left_pressed()
_handle_left_released()
_handle_right_pressed()
_handle_wheel()
```

The important part is to preserve the current **ordering and early-return semantics** exactly.

`_draw()` is another smaller Long Method candidate: grid, curve, points and handles can cleanly become `_draw_grid()`, `_draw_points()`, `_draw_handles()`.

# 6. P1 — Undo API has a Long Parameter List and Data Clump

This one is unusually clear.

`EasingCurveEditorUndo.commit_applied_action()` takes roughly this conceptual payload:

```text
undo_redo
curve
action_name
before
after
source_property
selection_restorer
before_selection
after_selection
before_point_resource_ids
after_point_resource_ids
```

That's **11 parameters**.

Refactoring.Guru flags more than three or four as a Long Parameter List, and repeated sets of variables as Data Clumps. ([Refactoring Guru][1])

You can see the same clump propagated through Inspector `_commit_curve_action()`.

The obvious cohesive object is something like:

```text
EasingCurveEditorAction
    before_state
    after_state
    before_selection
    after_selection
    before_point_resource_ids
    after_point_resource_ids
    selection_restorer
```

or possibly separate:

```text
EditorStateChange
SelectionChange
```

I would **not** make this a serialized Resource. A small editor-only `RefCounted` or typed Dictionary wrapper is enough.

# 7. P2 — Primitive Obsession / Data Clumps are widespread, but partially justified

Your snapshot architecture has lots of parallel primitive arrays:

```text
positions
left_control_points
right_control_points
handle_modes
locks
left_force_linear
right_force_linear
```

`make_point_snapshot()`, reversal, restoration, comparison, and mutation all manipulate variants of this group.

`_point_snapshot_differs()` is especially revealing because it receives nearly the entire group separately as parameters.

Refactoring.Guru specifically calls out string keys used as field names and recurring groups of primitives as Primitive Obsession/Data Clumps. ([Refactoring Guru][1])

However, **I would not eliminate your primitive serialization representation.**

It's there specifically to avoid nested-resource/live-debug problems. The smell is in letting that representation leak everywhere.

So I'd use:

```text
serialized snapshot = Dictionary / PackedArrays   ← keep
                     ↓
PointSnapshot accessor/mutator
                     ↓
rest of code
```

rather than replacing the storage format itself.

Your newer `POINT_PROPERTY_DEFINITIONS` table is already moving in the right direction: ordinary point properties can flow generically instead of each new property requiring edits to every snapshot function.

So I'd rate this **contained technical debt**, not a redesign target.

# 8. P2 — Inappropriate Intimacy between editor components

There are several instances of editor code directly using private Resource implementation details.

The Inspector restores:

```text
object._last_zoom
object._last_pan
object._last_slider_value
```

and connects graph signals directly to private Resource callbacks.

The graph itself writes:

```gdscript
_curve._last_slider_value = _zoom_step
```

directly.

The Undo helper knows about and invokes Resource internals such as:

```text
_set_editor_state_snapshot_with_point_resource_order
_begin_editor_parameter_edit
_cancel_editor_parameter_edit
_finish_editor_parameter_edit
```

That matches Refactoring.Guru's definition of **Inappropriate Intimacy**: one class using another's internal fields/methods. ([Refactoring Guru][3])

### Recommended direction

Don't necessarily make all those methods public.

A narrow editor bridge would be better:

```text
EasingCurveEditorBridge
    get_view_state()
    set_view_state()
    begin_parameter_edit()
    finish_parameter_edit()
    cancel_parameter_edit()
    restore_editor_snapshot()
```

Then only one component is intentionally coupled to those internals.

I would be conservative about actually moving `_last_zoom/_last_pan` out of the Resource until tests establish exactly what persistence behavior users expect.

# 9. Godot `EditorInspector` coupling is fragile but probably necessary

`EasingCurveEditorUndo` searches upward for an `EditorInspector` and then invokes the private/internal-looking:

```text
_edit_request_change
```

by name and emits `property_edited`.

That is technically Inappropriate Intimacy with Godot's editor implementation.

But this is a plugin and there are cases where public Godot APIs simply don't expose everything needed. I wouldn't remove a working workaround merely to satisfy a smell catalog.

I would instead **quarantine it** behind one tiny adapter/helper and regression-test it against supported Godot versions.

Then if Godot changes the internal API, there's one place to fix.

# Things I would *not* flag

`easing.gd` is ~32 KB, but it is largely a cohesive library of easing equations. Its size alone does **not** make it a Large Class smell.

Similarly, `EasingCurvePoint` is getting substantial, but most of its complexity revolves around one cohesive responsibility: point/handle invariants. I would actually move **more ownership of those rules toward it or a sibling point-domain helper**, not split it arbitrarily.

I found no convincing **Parallel Inheritance Hierarchies**, **Message Chains**, or **Middle Man** problem. The many `match` statements are worth watching, but enums like handle mode are a legitimate use of branching; I wouldn't introduce polymorphic class hierarchies solely to eliminate them.

There is also a minor duplicate conditional in `_parse_property()` for `"generate_tool_button"`, but that is cleanup-level, not architectural debt.

# Refactor order I recommend

I would refactor **before adding more significant transition or point-editing features**, but keep it incremental:

1. **Centralize point/snapshot mutation rules.** Eliminate the duplicated Handle Mode / Force Linear / Lock state machine from the Inspector. This is the highest-risk maintenance problem.
2. **Consolidate transition runtime metadata.** Make “add a transition” substantially closer to one definition + one implementation + tests.
3. **Break leaf classes out of the 102 KB Inspector file.** Move the self-contained nested UI controls first; leave the sensitive coordinator intact.
4. **Decompose `_gui_input()` and `handle_easing_curve_editor()`.** Pure Extract Method work, preserving exact behavior.
5. **Introduce an Undo action parameter object.** Collapse the before/after state/selection/resource-ID clump.
6. **Extract the pure Bézier solver from `EasingCurve`.** Reduces runtime class size with very little state-moving risk.
7. **Quarantine editor-private coupling.** One bridge for EasingCurve editor internals and one adapter for the Godot Inspector workaround.
8. **Only then reconsider larger ownership moves.** I would not touch the primitive serialization contract, notification state machine, or public resource API during the first refactor wave.

The key difference from a generic “these files are too big” audit is that **file size isn't the main issue**. The two things most likely to produce future bugs are **duplicated point invariants** and **transition knowledge scattered across registries/UI/implementation**. Fix those first and a lot of the apparent bloat becomes substantially easier to reason about.

Also, the repository's prior refactor document reports that its then-current validation reached all 17 registered test suites passing; I did **not** execute that suite against today's `c957be0` head, so I would use the current suite as the behavioral lock before starting these extractions.
