# v1.1.0 Code Smells Audit

Audit date: 2026-09-01  
Branch and commit: `dev` at `90e54c6`  
Project version: `1.1.0-dev`  
Godot version: `4.7.1.stable.official.a13da4feb`

## Executive assessment

The project has meaningful maintainability debt, but it does not need a broad
rewrite. The v1.0.7 refactor work successfully centralized transition metadata,
point-state rules, editor Undo/Redo context, graph-input dispatch, and the pure
Bezier solver. The highest-value v1.1.0 work is now concentrated at narrower
boundaries.

No P0 product-code smell was found. The release-confidence issue identified in
Finding 1 has been resolved: product suites now run in a generated host that
excludes unrelated development tooling. Follow-up validation also corrected the
original causal inference: Godot emits the environment-specific certificate
store diagnostic in the isolated product-only host, not only when the
development plugins are loaded.

Findings 2 and 3 are also resolved. The compiled Bezier cache now has one
focused owner, and Inspector Autofit now exposes an explicit request lifecycle
with tested completion, cancellation, stale-request, rebuild, fold, readiness,
and editor-destruction behavior.

| Priority | Finding | Primary smell | Recommendation |
| --- | --- | --- | --- |
| Resolved | Product tests were not isolated from development plugins | Hidden dependency / hidden side effects | Implemented a minimal generated test host |
| Resolved | Compiled Bezier cache state was spread across `EasingCurve` | Data clump / temporal coupling / divergent change | Extracted the compiled-segment cache boundary |
| Resolved | Inspector Autofit was an implicit asynchronous state machine | Temporal coupling / inappropriate intimacy | Consolidated scheduling, completion, and cancellation |
| Medium | Publish and Republish duplicate high-risk release steps | Duplicate code / shotgun surgery | Extract shared validation and publication steps while keeping flows distinct |
| Medium | Test suites duplicate their protocol and call private internals extensively | Duplicate code / inappropriate intimacy | Add a shared test case and narrow editor test driver incrementally |
| Accepted debt | Point snapshots remain parallel, string-keyed primitive arrays | Primitive obsession / data clump | Preserve compatibility; add validation and named keys rather than a new wrapper model |

## Scope

Reviewed:

- `addons/easing_curve/` runtime and editor code;

- `test/runners/`, `build_asset_store.ps1`, and `release.ps1`;
- `project.godot`, plugin metadata, changelog, and the previous v1.0.7 smell audit;
- the current registered 18-suite Godot test run.

Excluded except where they affect product validation:

- `_exports/`, because it contains generated distribution snapshots;
- `cpp/`, because it is reference/upstream Godot source rather than the addon

is supporting evidence, not a finding by itself.

## Findings

### 1. Resolved: product tests were coupled to unrelated development plugins

**Evidence**

- `project.godot:18-20` registers the `godot_ai` game helper as an autoload.
- `project.godot:29-31` enables Easing Curve together with `godot_ai` and
  `godot_ai_tunnel`.
- The suite runner launches that root project for every test at
  `test/runners/run_all_tests.ps1:206-215`.
- During the audit run, all 18 suites produced their expected `PASS:` marker
  and process exit code `0`, but every suite was classified as failed because
  Godot emitted the unclassified diagnostic
  `ERROR: Failed to read the root certificate store.`
- Editor-host output also showed the tunnel plugin starting and stopping a
  client process. Neither behavior belongs to the Easing Curve tests.

**Why it matters**

The strict diagnostic gate is valuable and should remain strict. The problem is
that the test host contains unrelated startup behavior. A certificate, network,
or tunnel change can make every product suite red without exercising different
Easing Curve behavior. That weakens the signal used to approve refactors and
releases and makes failures machine-dependent.

**Implemented remediation (2026-09-01)**

The runner now generates a project under `test/_temp/runner` containing only
the Easing Curve addon, test scripts, and test presets. It enables only the
Easing Curve plugin, initializes the isolated script-class cache with an Editor
import pass, and points every suite at that host while retaining per-suite logs,
timeouts, process isolation, and unexpected-diagnostic failure policy. Failed
runs preserve the generated project and diagnostics; successful runs remove
them.

Running the CSS suite directly in the isolated product-only host reproduced the
exact `ERROR: Failed to read the root certificate store.` message without any
development plugin or tunnel output. The runner therefore classifies only that
exact Godot 4.7.1 host diagnostic; it does not broadly allowlist certificate,
network, plugin, or tunnel errors.

**Acceptance evidence**

- No `godot_ai` or tunnel startup output appears in product test logs.
- All 18 suites pass the aggregate runner, not only their internal assertions.
- The three intentional serialization errors and existing Editor-host shutdown
  diagnostics remain narrowly classified.

### 2. Resolved: the compiled Bezier cache was a parallel data clump with implicit invalidation

**Evidence**

Before extraction, `EasingCurve` was 3,056 lines and owned several different
domains. The most reviewable extraction candidate was the recently added
compiled segment cache:

- cache validity and storage occupy the parallel fields at
  `addons/easing_curve/scripts/runtime/easing_curve.gd:536-543`;
- geometry invalidation increments one revision and resets the locality index
  at `easing_curve.gd:2334-2341`;
- sampling assumes those arrays have matching indices at
  `easing_curve.gd:2570-2610` and `easing_curve.gd:2664-2686`;
- compilation fills four arrays in lockstep and advances the compiled revision
  at `easing_curve.gd:2613-2644`;
- `_sample_raw()` may first repair exposed point-array topology and emit change
  notifications at `easing_curve.gd:2509-2512`, so a method reached through
  `sample()` is not operationally pure.

**Why it matters**

The x bounds, x controls, y bounds, y controls, safety flag, revision, and last
segment index form one cache object but are maintained as independent owner
fields. A future performance change must preserve their lengths, ordering,
invalidation, fallback behavior, and locality optimization together. Missing a
dirty path can return stale samples rather than failing loudly.

This was also the clearest remaining reason `EasingCurve` changed for unrelated
purposes: serialization, editor transactions, presets, point topology,
notifications, and sampling-cache policy all lived in the same resource.

**Implemented remediation (2026-09-01)**

The new private `easing_curve_compiled_segments.gd` helper owns only:

- the four compiled arrays;
- binary-search eligibility;
- compiled revision and last-segment locality;
- compile, invalidate, segment lookup, and compiled sampling.

Point ownership, serialized snapshots, public `sample()` methods, and the
fallback reference path remain in `EasingCurve`. The resource now owns one
compiled-segment collaborator and invalidates it through one explicit method,
removing the parallel cache fields without changing the public resource API or
serialized data.

The compatibility side effect is now named
`_synchronize_exposed_points_before_sampling()`, making topology repair and its
possible notification visible at the sampling call site. Runtime tests assert
behavior after point geometry edits, notification-suppressed preview edits, and
in-place topology mutation without reading revision fields from `EasingCurve`.

### 3. Resolved: Inspector Autofit was an implicit asynchronous state machine

**Evidence**

- The Inspector owns `_initial_autofit_resource_ids`, `_autofit_pending`, and
  `_autofit_request_id` at
  `addons/easing_curve/scripts/editor/inspector/easing_curve_editor_inspector_plugin.gd:444-446`.
- Inspector reconstruction suppresses graph rendering when a request is pending
  at `easing_curve_editor_inspector_plugin.gd:822-826`.
- `_queue_autofit_curve_editor()`, fold callbacks, two `process_frame` waits,
  request-id cancellation, `_slider` readiness, and render unsuppression are
  coordinated across `easing_curve_editor_inspector_plugin.gd:2409-2470`.
- The Inspector directly reaches into graph-editor and resource underscore
  members, including `_slider`, `_last_zoom`, `_last_pan`, and preview helpers
  around `easing_curve_editor_inspector_plugin.gd:828-905` and
  `easing_curve_editor_inspector_plugin.gd:1373-1386`.

**Why it matters**

Correct behavior depends on ordering across Inspector rebuilds, folding,
deferred calls, two frames of layout, slider creation, and graph suppression.
Several early-return paths intentionally leave work pending, but the state
contract is not represented in one place. Changes to layout or fold behavior
can therefore leave the graph suppressed, perform a stale fit, or make a first
open behave differently from later rebuilds.

This responsibility also added lifecycle and view-state reasons for the already
large Inspector controller to change.

**Implemented remediation (2026-09-01)**

The workflow is consolidated locally into `_request_autofit()`,
`_cancel_autofit()`, `_is_current_autofit_request()`, `_is_autofit_ready()`, and
`_complete_autofit()`. State mutation and render suppression now pass through
those operations. A stale coroutine transfers ownership to the newer request;
a folded editor deliberately remains pending; missing readiness, a missing
SceneTree, or editor destruction cancels the current request; and completion or
cancellation releases suppression.

The local operations were sufficient, so no additional coordinator abstraction
was added. `EasingCurveEditor` now exposes `is_autofit_ready()`,
`set_position_x_order_preview()`, and `clear_position_x_order_preview()`, and the
Inspector uses the existing public slider setter instead of reaching into those
underscore members.

Focused characterization now covers stale requests, fold/unfold, Inspector
rebuild, missing slider, editor destruction, immediate suppression, and release
after completion or cancellation.

### 4. Medium: Publish and Republish duplicate high-risk release logic

**Evidence**

`release.ps1` is 880 lines. `Invoke-Publish()` begins at line 508 and
`Invoke-Republish()` at line 610. Both flows independently implement several of
the same decisions:

- branch and clean-tree checks;
- `git fetch` and remote-only commit checks;
- GitHub CLI availability;
- changelog release-note extraction and temporary-file lifecycle;
- tag/branch publication;
- GitHub release metadata and asset handling;
- post-operation verification and reporting.

The duplicated blocks already differ in indentation and command layout around
`release.ps1:592-603` versus `release.ps1:740-755`, which makes visual comparison
harder.

**Why it matters**

Release code is low-frequency, externally mutating, and difficult to exercise
safely. A new precondition or verification can be added to one path and omitted
from the other. That is shotgun surgery in the workflow with the highest cost
of an unnoticed mistake.

**Smallest effective remediation**

Keep Publish and Republish as separate top-level flows and preserve their
different confirmation and force semantics. Extract only shared, reviewable
steps:

- assert release branch and remote currency;
- create and dispose the release-notes file;
- verify a local and remote annotated tag target;
- update or create GitHub release metadata through a narrowly named helper.

Pure parsing and validation helpers can receive lightweight tests without
executing Git, `gh`, or publishing. Do not merge the two workflows into a flag-
heavy generic function.

### 5. Medium: tests duplicate their protocol and are tightly coupled to private editor structure

**Evidence**

- The 19 `test/scripts/*.gd` files contain about 8,461 lines.
- Most suites independently declare `_failures`, `_checks`, `_expect()`, print a
  `PASS:` marker, and quit the tree.
- There are 88 explicit `call("_...")` invocations in the test scripts and 341
  underscore-member references in total. These cover Inspector transaction,
  selection, Autofit, toolbar, gesture, and layout internals.
- `editor_host_test_harness.gd` centralizes Editor-host acquisition, but there
  is no equivalent shared assertion/result protocol or editor interaction
  driver.

**Why it matters**

Changing the runner protocol requires edits across many suites. More
importantly, routine private method extraction or renaming can break dozens of
tests even when observable behavior is unchanged. This raises the cost of the
very editor refactors the suite is intended to protect.

Some white-box access is justified because Godot Editor interaction is hard to
drive headlessly. The smell is the breadth of the coupling, not the existence
of any private access.

**Smallest effective remediation**

Introduce a shared `test_case.gd` base (or composed assertion helper) for check
counting, failures, PASS output, and exit behavior. Migrate suites only when
they are next edited.

For editor tests, add a narrow `EasingCurveEditorTestDriver` that exposes
intent-level actions such as select point, commit edit, request Autofit, and
reorder point. Keep direct private calls only for tests whose purpose is the
private state transition itself.

## Accepted compatibility debt: primitive point snapshots

Point snapshots remain dictionaries of parallel packed arrays and string keys.
There are approximately 93 direct snapshot key reads/writes across
`easing_curve.gd`, `easing_curve_point_snapshot_mutator.gd`, the Inspector, and
Undo/Redo code. A semantic point field can affect capture, reverse/invert,
restore, diffing, editor mutation, and serialization behavior.

This is a real primitive-obsession/data-clump smell, but it is deliberately a
compatibility boundary. The existing `POINT_PROPERTY_DEFINITIONS`, lifecycle
classification, snapshot mutator, and serialization contract tests materially
reduce the risk. Replacing the dictionaries with serialized Resource objects or
adding a second synchronized wrapper model would cost more than it clarifies.

Recommended containment:

- define named `StringName` constants for the semantic snapshot keys;
- add one `validate_point_snapshot()` boundary check for required keys, packed
  array types, and equal lengths;
- require a contract-test update whenever a semantic snapshot field is added;
- keep the current external keys and packed-array representation unchanged.

## Improvements confirmed since the previous audit

The following earlier smells are no longer priority findings:

- transition runtime metadata is centralized in `TRANSITION_DEFINITIONS`;
- point Handle Mode, Control State, Force Linear, and Lock rules route through
  `easing_curve_point_state_transition.gd` and the snapshot mutator;
- `_gui_input()` is decomposed into gesture-specific handlers;
- Undo/Redo uses `ActionContext` instead of the former long parameter list;
- pure Bezier root solving is isolated in `bezier_solver.gd`;
- Inspector leaf controls were moved to focused scripts.

These boundaries should be preserved. Their existence is why the audit does
not recommend splitting `EasingCurve` or the Inspector wholesale.

## Recommended remediation order

1. Deduplicate shared release validation and publication helpers.
2. Introduce the shared test protocol, then migrate private editor calls only
   as affected suites are touched.
3. Add snapshot constants and validation alongside the next snapshot feature;
   do not schedule a standalone representation rewrite.

## Open questions and assumptions

- The `godot_ai` addons are assumed to be local development tooling rather than
  part of the distributed Easing Curve addon.
- In-place mutation of the public `points` array is assumed to remain a
  compatibility requirement, so the sampling-time synchronization fallback is
  not proposed for removal.
- Snapshot field names and packed-array types are assumed to be serialized and
  live-debug compatibility contracts.
- Underscore-prefixed methods and fields are treated as private conventions,
  even though GDScript does not enforce private visibility.
