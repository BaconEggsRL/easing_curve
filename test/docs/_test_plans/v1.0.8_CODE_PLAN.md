# Easing Curve v1.0.8 Code Plan

## 1. Release goals

The v1.0.8 cycle has two goals:

1. Add axis-constrained dragging for graph points and Bézier control handles.
2. Take a small, behavior-preserving maintainability pass over the current
   post-v1.0.7 baseline.

This document records the fresh code-smells audit performed on 2026-08-26. It
is the authoritative working plan for v1.0.8. It is not authorization for a
broad redesign, serialized-data change, public-API break, or speculative
framework.

The audit found **4 high-yield/low-risk opportunities**, **4 worthwhile but
more invasive opportunities**, and **8 areas that should be left alone**.

## 3. Preservation / compatibility constraints

Every v1.0.8 change must preserve:

- serialized `EasingCurve` resources and flat point-property storage;
- point snapshot, function snapshot, and editor-state snapshot shapes;
- `TRANS`, `EASE`, Handle Mode, Control Side, and Control State numeric values;
- point Resource identity, ordering, stable equal-X behavior, and endpoint
  takeover;
- point/control geometry for every Handle Mode, lock, and Force Linear
  combination;
- function, CSS, Bézier, transition, ease, reverse, and invert sampling;
- graph/Points-list/Inspector selection synchronization;
- Undo/Redo action names, transaction boundaries, no-op handling, selection
  restoration, and point Resource order restoration;
- `changed`, `points_changed`, property-list refresh, Inspector edit, and
  live-debug notification behavior;
- deferred parameter editing and generated-function behavior;
- per-resource graph pan/zoom/selection restoration;
- current Inspector focus, fold, layout, drag/drop, and deferred editor
  workarounds;
- all existing public classes, methods, signals, constants, properties, and
  callable signatures unless a separate compatibility decision explicitly
  approves deprecation.

No production/test change should be justified solely by file size, lack of an
internal reference to a public symbol, or structural similarity between
semantically distinct operations.

## 4. Code-smells audit methodology

The audit used the
[Refactoring.Guru code-smell catalog](https://refactoring.guru/refactoring/smells)
as a taxonomy for bloaters, change preventers, dispensables, coupling, and
conditional complexity. A catalog label was not sufficient evidence by itself.

The review included:

- every Easing Curve runtime, point, easing, graph, Inspector, Undo/Redo,
  update-checker, helper, and shipped test-scene script;
- supporting scenes/resources where ownership or serialized behavior is
  relevant;
- the complete automated suite, its launcher, editor-host harness, test
  documentation, and non-runner test assets;
- repository-wide reference searches for methods, fields, constants, property
  names, commented implementation, and debug remnants;
- function-responsibility and long-method inspection;
- comparison with tag `v1.0.7`, recent history/blame, and the archived v1.0.6
  and v1.0.7 decisions;
- coverage mapping before proposing any production cleanup.

The unrelated `addons/godot_ai` implementation was not audited as Easing Curve
production code. Its effect on the test environment was recorded because it is
enabled by this development project's `project.godot`.

Each suspected smell was classified as a real opportunity, an intentional
constraint, or not worth changing. The findings below record all actionable
items and the important false positives that future audits should not reopen.

## 5. Findings

### 5.1 High-yield / low-risk

#### CLEANUP-01 — Reference-proven dead and unreachable implementation remnants

- **Location:**
  - `addons/easing_curve/easing_curve_editor_plugin.gd:23`
    (`_pending_update`);
  - `addons/easing_curve/inspector/deferred_parameter_editor_property.gd:14`
    and `:105-127` (`reset_button`, `_on_reset_pressed()`, and
    `_update_reset_button()`);
  - `addons/easing_curve/scripts/point.gd:634`
    (`_initialize_default_handles()`);
  - `addons/easing_curve/scripts/easing_curve_editor.gd:1014`
    (`_bezier()`);
  - `addons/easing_curve/easing_curve_editor_inspector_plugin.gd:952-959`
    (the second `generate_tool_button` branch);
  - small commented implementation remnants in the graph, Inspector, and
    shipped test scene.
- **Smell/category:** Dead Code / Duplicate Conditional / Obsolete Commented
  Implementation.
- **Concrete evidence:** `_pending_update`, `_initialize_default_handles()`, and
  graph `_bezier()` have no runtime/test call sites. The deferred property
  `reset_button` is never assigned or connected, so its reset handler is
  unreachable and its update helper always returns at the null guard. The first
  `generate_tool_button` branch always returns `true`, making the immediately
  following identical condition unreachable. The graph's local `_bezier()`
  became stale after v1.0.7 moved Bézier math to `bezier_solver.gd`.
- **Why it matters here:** These remnants obscure the real extension points in
  already-sensitive editor code. The deferred-property reset path in particular
  looks supported even though the native Inspector owns reset behavior.
- **Proposed improvement:** Remove only the reference-proven private remnants
  and their no-op call sites. Collapse the duplicate property branch. Remove
  stale commented statements while retaining licensing, compatibility, and
  workaround rationale. Do not include public unreferenced helpers in this
  cleanup.
- **Expected payoff:** A smaller false surface area for future editor changes
  and less time spent tracing inactive paths.
- **Implementation effort:** Low.
- **Regression risk:** Low.
- **Confidence:** High.
- **Tests/behavior to protect:** Script parse/load; deferred parameter edit and
  reset behavior; graph rendering/sampling; generated Jitter/Irregular control;
  full 17-suite run; visible Inspector parameter reset smoke.
- **Dependencies:** None.

#### METADATA-01 — The zoom model is duplicated in three classes

- **Location:**
  - `addons/easing_curve/scripts/easing_curve.gd:47-54`;
  - `addons/easing_curve/scripts/easing_curve_editor.gd:31-35`;
  - `addons/easing_curve/scripts/zoom_slider_container.gd:12-16`.
- **Smell/category:** Duplicate Code / Shotgun Surgery / Duplicated Defaults.
- **Concrete evidence:** All three declare the same `ZOOM_MIN`, `ZOOM_MAX`,
  `ZOOM_FACTOR`, `ZOOM_STEPS`, and `DEFAULT_SLIDER_VALUE` formulas. The graph
  uses these values to configure wheel/slider behavior while the Resource uses
  the duplicate default to persist the graph's per-resource view state. The
  slider container's copies are currently not used internally but are exposed
  by its public `class_name`.
- **Why it matters here:** A future zoom-range or multiplier change can silently
  desynchronize slider limits, wheel steps, and the restored default. The
  duplicated public constants cannot simply be deleted without an API decision.
- **Proposed improvement:** Keep the existing public constant names but make
  them aliases of one authoritative definition, using the current
  `EasingCurve` constants as the least disruptive owner. Add a contract check
  proving all public aliases remain equal.
- **Expected payoff:** One edit for future zoom behavior and no drift between
  graph, slider, and stored view-state defaults.
- **Implementation effort:** Low.
- **Regression risk:** Low.
- **Confidence:** High.
- **Tests/behavior to protect:** Existing public constant names/values; default
  slider position; wheel and slider zoom; autofit; zoom-around-pointer; pan/zoom
  persistence across Inspector refresh/resource switching; graph gesture suite;
  visible pan/zoom smoke.
- **Dependencies:** None.

#### TEST-02 — The test launcher is coupled to one absolute Godot installation path

- **Location:** `test/scripts/run_godot.ps1:22`.
- **Smell/category:** Hard-Coded Dependency / Environment Coupling.
- **Concrete evidence:** The launcher assigns one absolute executable path:
  `C:\Godot\4.7\engine\Godot_v4.7.1-stable_win64.exe\Godot_v4.7.1-stable_win64_console.exe`.

- **Why it matters here:** The wrapper is the required gateway for all 17

  engine is found. Do not weaken the wrapper's log, exit-code, or error-dialog
  behavior.
- **Expected payoff:** Reproducible local/CI execution without tracked edits.
- **Implementation effort:** Low.
- **Regression risk:** Low.
- **Confidence:** High.
- **Tests/behavior to protect:** Successful explicit-path launch; current-path
  fallback; clear invalid-path failure; exact Godot exit-code propagation;
  unique `.godot/test_logs` handling; timeout/process-tree cleanup; complete
  17-suite run.
- **Dependencies:** None.

### 5.2 Worthwhile but more invasive

#### EDITOR-01 — `_apply_point_property_change()` is still a multi-responsibility coordinator

- **Location:**
  `addons/easing_curve/easing_curve_editor_inspector_plugin.gd:2153-2280`.
- **Smell/category:** Long Method / Divergent Responsibility / Complex
  Conditional Dispatch.
- **Concrete evidence:** In roughly 130 lines the method starts/coalesces an
  edit transaction, captures selection and Resource IDs, reads a primitive
  snapshot, applies position translation, applies paired-handle geometry,
  dispatches semantic state changes, handles ordinary-property fallback,
  controls draft notifications, performs Position-X order preview/commit, and
  selects the Undo/Redo completion path. Several semantic property branches
  contain the same `POINT_SNAPSHOT_MUTATOR.apply(...)` call.
- **Why it matters here:** The method is the junction between point semantics,
  Inspector refresh, ordering, and Undo/Redo. A new point property or drag
  behavior must be placed correctly among transaction and notification steps,
  making local changes harder to review.
- **Proposed improvement:** Extract one private, side-effect-limited snapshot
  mutation helper that returns success. Keep transaction capture, snapshot
  publication/reorder, and commit ordering visible in the coordinator. Group
  properties that intentionally route through `POINT_SNAPSHOT_MUTATOR`, but do
  not genericize position/control geometry or reorder semantics.
- **Expected payoff:** A shorter transaction method with clearer ownership and
  a single reviewable mutation boundary.
- **Implementation effort:** Medium.
- **Regression risk:** Medium.
- **Confidence:** High.
- **Tests/behavior to protect:** Point state characterization; control
  editability; Position-X drag/reorder/endpoint takeover; Linear control alias;
  selection refresh; point property copy/paste/reset; graph gestures;
  Undo/Redo action counts and names; notification counts; full suite and visible
  Inspector smoke.
- **Dependencies:** Prefer CLEANUP-01 first. This is not required for
  axis-constrained dragging.

#### EDITOR-02 — Point dragging repeats handle-translation responsibility across layers

- **Location:**
  - graph `EasingCurveEditor._handle_drag_motion()` at
    `addons/easing_curve/scripts/easing_curve_editor.gd:210-243`;
  - live point `EasingCurvePoint.set_position()` at
    `addons/easing_curve/scripts/point.gd:175-202`;
  - Inspector snapshot position branch at
    `addons/easing_curve/easing_curve_editor_inspector_plugin.gd:2171-2192`.
- **Smell/category:** Duplicate Domain Logic / Feature Envy / Excessive
  Notification Work.
- **Concrete evidence:** On a point drag the graph captures both controls,
  requests the new position, then requests each unlocked control at
  `old_control + delta`. Both the live `set_position()` fallback and the
  Inspector's position snapshot branch already translate unlocked controls by
  the same delta. A connected Inspector path can therefore process up to three
  property-change requests and snapshots per mouse-motion event for one logical
  point move.
- **Why it matters here:** The graph knows a point invariant already owned by
  both mutation paths. That increases per-motion work and creates three places
  to update when movement rules change. It is especially visible when adding a
  coordinate constraint to the logical point target.
- **Proposed improvement:** First add characterization for emitted
  `point_property_change_requested` sequences and curve/Inspector notification
  counts. If no supported contract requires the two redundant handle requests,
  let the position mutation path be the sole handle-translation owner. If the
  signal sequence is externally relied on, document it and leave the code.
- **Expected payoff:** One logical mutation per point-drag motion, simpler axis
  constraint application, and less snapshot/refresh work.
- **Implementation effort:** Low to Medium.
- **Regression risk:** Medium because the graph signal is public and
  notification timing is compatibility-sensitive.
- **Confidence:** Medium.
- **Tests/behavior to protect:** Connected-Inspector and no-listener fallback
  paths; all handle modes; each control lock combination; Force Linear;
  point/control signal sequence; live-debug and `changed`/`points_changed`
  counts; one Undo action per drag; ordering/endpoint preview; full suite.
- **Dependencies:** Characterization coverage first. EDITOR-01 would make the
  result easier to read but is not required. Do not block the axis feature on
  this refactor.

#### EDITOR-03 — Graph `_draw()` combines independent rendering responsibilities

- **Location:** `addons/easing_curve/scripts/easing_curve_editor.gd:493-625`.
- **Smell/category:** Long Method / Multiple Responsibilities.
- **Concrete evidence:** One method updates transforms, draws borders and grid,
  chooses function versus Bézier rendering, builds preview ordering, and draws
  points plus left/right control lines and hover/selection states. Existing
  curve-specific rendering is already extracted, but grid and point/control
  rendering remain embedded.
- **Why it matters here:** Axis-constrained movement may benefit from a small
  visual constraint cue. Adding another draw phase directly to this method
  would increase ordering and state noise even though grid and control rendering
  have clear boundaries.
- **Proposed improvement:** Extract `_draw_grid()` and
  `_draw_points_and_controls(display_points)` while retaining the current
  top-level draw order. Add an axis guide only if the feature design calls for
  one; do not build a renderer abstraction.
- **Expected payoff:** Clear draw-layer order and an isolated place for any
  future drag overlay.
- **Implementation effort:** Low.
- **Regression risk:** Medium because pixel/layout behavior is primarily
  manually observed.
- **Confidence:** High.
- **Tests/behavior to protect:** Function and Bézier graph rendering; pending
  add and Position-X preview ordering; first/last handle visibility; selection
  and hover colors; pan/zoom; high-DPI editor scale; visible narrow/wide
  Inspector smoke. The current automated suite does not provide pixel-level
  coverage.
- **Dependencies:** None. Perform only if the axis feature needs a visual layer
  or the standalone clarity payoff is accepted.

#### UNDO-01 — Undo registration duplicates two backend-specific method trees

- **Location:**
  `addons/easing_curve/scripts/easing_curve_editor_undo.gd:43-153`.
- **Smell/category:** Duplicate Conditional Fragments / Long Method / Godot API
  Coupling.
- **Concrete evidence:** `commit_applied_action()` separately registers
  Resource-order restoration for `EditorUndoRedoManager` and fallback
  `UndoRedo`, then repeats the same backend split for selection restoration.
  Snapshot duplication, target method names, before/after direction, and
  argument binding appear in mirrored do/undo blocks.
- **Why it matters here:** Any additional action participant or restoration
  payload must be added symmetrically to both Godot APIs. An asymmetry can pass
  fallback tests while failing in the real Editor host, or vice versa.
- **Proposed improvement:** Extract narrow private registration helpers for the
  two existing restoration operations. Keep `ActionContext`, primitive
  snapshots, backend detection, commit ordering, and Inspector/live-debug calls
  unchanged. Do not introduce a generalized command framework.
- **Expected payoff:** Less duplicated sensitive code and a clearer audit trail
  for do/undo symmetry.
- **Implementation effort:** Medium.
- **Regression risk:** Medium.
- **Confidence:** Medium.
- **Tests/behavior to protect:** Both `UndoRedo` and
  `EditorUndoRedoManager` paths; point Resource identity/order; selection before
  and after add/remove/reorder; no-op actions; parameter begin/finish/cancel;
  `_edit_request_change` and `property_edited` live-debug behavior; full suite
  and visible Editor Undo/Redo smoke.
- **Dependencies:** None. Not a prerequisite for v1.0.8 feature work.

### 5.3 Leave alone

#### LEAVE-01 — Primitive point/function/editor snapshots and their restore order

- **Location:** `EasingCurve` snapshot constants and methods, primarily
  `addons/easing_curve/scripts/easing_curve.gd:156-524` and `:1551-2263`.
- **Smell/category:** Apparent Primitive Obsession / Data Clumps / Long
  Parameter Lists.
- **Concrete evidence:** Snapshots use string-keyed Dictionaries and parallel
  PackedArrays, and restore/difference methods pass the same groups. These
  values cross serialization, Inspector/live-debug, and Undo/Redo boundaries,
  and tests lock their names, types, order, Resource-free shape, old-key
  defaults, and restoration sequence.
- **Why it should remain:** A wrapper/object layer would retain the same wire
  format while adding a conversion and synchronization contract. v1.0.7 already
  quarantined ordinary-property bookkeeping behind descriptors and kept
  semantic fields explicit.
- **Proposed improvement:** None for v1.0.8. Add only focused accessors when a
  concrete new property proves they remove repeated behavior.
- **Expected payoff of leaving alone:** Maximum serialization/live-debug
  compatibility with no speculative layer.
- **Implementation effort:** High for a redesign.
- **Regression risk:** High.
- **Confidence:** High.
- **Tests/behavior to protect:** Serialization/transition contracts, legacy
  fixtures, all snapshot round trips, notification counts, transforms,
  Resource-free editor snapshots, Undo/Redo.
- **Dependencies:** This constraint governs EDITOR-01, EDITOR-02, and UNDO-01.

#### LEAVE-02 — `EasingCurve` remains the owner of topology, persistence, notifications, and public orchestration

- **Location:** `addons/easing_curve/scripts/easing_curve.gd` as a whole.
- **Smell/category:** Apparent Large Class / Divergent Change.
- **Concrete evidence:** The Resource owns public parameters/sampling, point
  topology, flat storage, snapshots, transforms, notifications, and editor
  transaction state. The pure Bézier solver was already extracted in v1.0.7;
  the remaining responsibilities share serialized state and notification
  ordering.
- **Why it should remain:** Splitting storage, topology, or notification state
  would create multiple authorities around Godot's Resource/property-list
  lifecycle. No remaining boundary has the same low coupling and pure inputs as
  the extracted solver.
- **Proposed improvement:** Keep bounded Extract Method changes local. Do not
  split the Resource merely to reduce line count.
- **Expected payoff of leaving alone:** One compatibility authority for Resource
  state and fewer cross-object transaction hazards.
- **Implementation effort:** High for a split.
- **Regression risk:** High.
- **Confidence:** High.
- **Tests/behavior to protect:** Entire automated suite plus legacy save/load and
  visible Inspector/live-debug smoke.
- **Dependencies:** LEAVE-01.

#### LEAVE-03 — Live point setters and snapshot mutator intentionally have different policy surfaces

- **Location:** `addons/easing_curve/scripts/point.gd` and
  `addons/easing_curve/scripts/easing_curve_point_snapshot_mutator.gd`.
- **Smell/category:** Apparent Duplicate Code / Parallel State Machines.
- **Concrete evidence:** Both understand Handle Mode, Force Linear, and locks,
  but the snapshot mutator also enforces Inspector interaction policy such as
  linked-side sharing and last-action-wins lock/Force Linear normalization.
  Public runtime setters retain independently settable Resource state.
- **Why it should remain:** Making the Inspector mutate live points directly
  would break the primitive snapshot/Undo/live-debug boundary. Forcing both
  paths through one policy would risk changing supported runtime setter
  behavior. v1.0.7 deliberately centralized Inspector semantic mutation without
  moving live ownership.
- **Proposed improvement:** None unless a concrete semantic discrepancy is
  identified and characterized. Shared pure geometry helpers remain acceptable
  when both paths demonstrably use identical math.
- **Expected payoff of leaving alone:** Clear separation between public runtime
  state and editor interaction policy.
- **Implementation effort:** Medium to High for further consolidation.
- **Regression risk:** High.
- **Confidence:** High.
- **Tests/behavior to protect:** Point state characterization, direct point API,
  control editability, Inspector lock/Force Linear order, snapshots, Undo/Redo.
- **Dependencies:** LEAVE-01.

#### LEAVE-04 — Built-in Bézier preset generation stays in `EasingCurve`

- **Location:** `EasingCurve._create_canonical_preset()`,
  `cubic_bezier()`, `cubic_bezier_pair()`, `_set_composed_bezier_preset()`, and
  `_update_preset()` at `addons/easing_curve/scripts/easing_curve.gd:1337-1453`
  and `:2731-2826`.
- **Smell/category:** Apparent Long Match / Large Class.
- **Concrete evidence:** The match is long, but each branch maps one transition
  and ease mode to compatibility-tested geometry. It constructs real
  `EasingCurvePoint` Resources through normal topology/notification paths and
  applies persistent transforms afterward.
- **Why it should remain:** The v1.0.7 audit already found that extracting only
  fixed control vectors would add an EasingCurve-specific factory contract for
  little reduction, while moving the full method would couple a factory back to
  live Resource mutation and notifications.
- **Proposed improvement:** None. Add a new explicit branch only for a genuine
  new built-in Bézier transition and protect its geometry.
- **Expected payoff of leaving alone:** Preserved canonical geometry and one
  mutation path for live and reset generation.
- **Implementation effort:** Medium for extraction.
- **Regression risk:** High.
- **Confidence:** High.
- **Tests/behavior to protect:** Tween equivalence, canonical preset/reset,
  Back overshoot, transforms, endpoint counts, serialization.
- **Dependencies:** LEAVE-02.

#### LEAVE-05 — Per-resource graph view state remains non-serialized Resource state

- **Location:** `EasingCurve._last_slider_value`, `_last_zoom`, `_last_pan`, and
  callbacks; Inspector graph construction; graph zoom application.
- **Smell/category:** Apparent Inappropriate Intimacy / Runtime-Editor Coupling.
- **Concrete evidence:** The Inspector restores private view values when rebuilt,
  and graph/Resource callbacks update them. The values are deliberately absent
  from serialized snapshots and persist only for the lifetime of the Resource
  instance.
- **Why it should remain:** v1.0.6/v1.0.7 assessed this boundary. Moving it to a
  static editor cache would introduce a second per-Resource authority and stale
  instance cleanup without reducing the update/restore contract.
- **Proposed improvement:** None in v1.0.8. METADATA-01 may remove duplicated
  constants without moving ownership.
- **Expected payoff of leaving alone:** Per-resource refresh persistence without
  serialization or cache lifecycle.

## 7. Axis-constrained dragging notes

### 7.1 Current architecture assessment

No prerequisite gesture-framework refactor is justified. The v1.0.7
decomposition already exposes the useful boundaries:

```text
_handle_left_pressed()
    -> establishes selected point/control and drag state

_handle_drag_motion()
    -> converts view position to world target
    -> checks locks
    -> requests point/control mutation

_handle_left_released()
    -> closes one edit transaction and commits final ordering
```

Axis selection belongs between world-target calculation and the existing clamp
and mutation request. It should not alter Inspector snapshot ownership,
point-domain Handle Mode behavior, or Undo/Redo boundaries.

### 7.2 Feature design decisions to settle before implementation

- Choose the modifier and whether it locks the dominant axis or selects an
  explicit axis. The current requirement says “a modifier,” but does not define
  the exact interaction.
- If using dominant-axis locking, determine it from total displacement from a
  stable drag origin after a small threshold, not from the latest frame delta;
  otherwise the constrained axis can flip during a drag.
- Define whether pressing/releasing the modifier mid-drag preserves continuity.
  Avoid jumps by retaining the original grab offset/origin.
- Decide whether a visual axis cue is required. If yes, use a small dedicated
  draw phase; do not create a generalized gesture renderer.
- Keep point and handle constraints on the requested target only. Balanced,
  Mirrored, Linked, Force Linear, and lock consequences remain owned by the
  existing point/snapshot mutation paths.

### 7.3 Required feature coverage

Add graph characterization for:

- unconstrained point and left/right handle dragging remains byte-for-behavior
  equivalent;
- horizontal and vertical point constraints;
- horizontal and vertical control-handle constraints;
- modifier pressed before drag, pressed during drag, released during drag, and
  released at gesture completion;
- stable dominant-axis choice near the threshold, if that design is selected;
- view/world correctness under pan and zoom;
- clamping at X endpoints and Y range limits;
- point-order crossing and endpoint takeover while horizontally constrained;
- no order change while vertically constrained;
- position/control locks and Force Linear;
- Free, Linear fallback, Balanced, Mirrored, and Linked handle modes;
- one Undo action per completed drag, no action for a no-op drag, and correct
  Undo/Redo selection/resource identity;
- right-delete, pending-add, pan, wheel zoom, hover, and function-mode input
  remain unchanged.

### 7.4 Cleanup prerequisite decision

**No cleanup must precede axis-constrained dragging.** EDITOR-02 could reduce
redundant per-motion requests, and EDITOR-03 could make a visual cue easier, but
both carry behavior or visual risk that should remain separate. The feature can
be implemented safely by constraining the existing world target inside
`_handle_drag_motion()` and preserving the current request/commit sequence.
