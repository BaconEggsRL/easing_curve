# Easing Curve v1.1.0 Code Tracker

This tracker is the v1.1.0 architecture-improvement plan and future execution
record. It follows `test/docs/_CODE_WORKFLOW_REQUIREMENTS.md`.

No production implementation is authorized by creation of this document. Each
production step remains a separate approval gate with the exact-file / precise-edit
packet required by the workflow.

## 1. Release Charter [FROZEN]

### 1.1 User-confirmed v1.1.0 goals

v1.1.0 is an architecture-improvement release focused on the two dominant
coordination classes rather than new product behavior.

The user supplied the following direction:

1. Treat the current `EasingCurve` and Inspector controller as genuine
   Large Class / Divergent Change risks, with localized Inappropriate Intimacy
   where editor code reaches across ownership boundaries.
2. Keep `EasingCurve` as the compatibility-facing public resource façade.
3. Preserve all serialized keys and existing compatibility contracts while
   delegating internal responsibilities toward:
   - a preset / transition geometry factory;
   - serialization and snapshot codec support;
   - one point-state transition authority;
   - editor-session / view-state support;
   - smaller Inspector point-list, graph-integration, clipboard, and transaction
     controllers.
4. Do not perform a one-shot rewrite. Extract one characterized, tested
   responsibility at a time.

### 1.2 Architecture review of the proposed goals

The overall direction is sound, but the current code changes two parts of the
initial decomposition plan:

- **The point-state transition authority already exists and should be preserved,
  not extracted again.** `easing_curve_point_state_transition.gd` is the pure
  Handle Mode / Control State / Force Linear / Lock authority. `point.gd` uses
  it for live behavior and `easing_curve_point_snapshot_mutator.gd` adapts
  snapshot/Inspector intent to the same authority. Re-splitting this domain
  would create duplication instead of reducing it.
- **Do not combine all editor-only state into one new object merely because it
  is editor-related.** Transient graph view values (`slider`, `zoom`, `pan`) and
  change-batching / edit-session counters have different reasons to change.
  v1.1.0 should extract them as separate small responsibilities instead of
  replacing one Large Class with a smaller editor-state god object.
- **Do not create a second graph controller by default.** `EasingCurveEditor`
  already owns graph behavior. After the point-list, clipboard, and transaction
  extractions, reassess the Inspector's remaining graph-facing orchestration.
  Create only a narrow graph-integration bridge if a coherent residual boundary
  still exists. Do not move graph behavior out of `EasingCurveEditor` merely to
  satisfy a target class list.

These refinements apply the requested problem-first, incremental approach:
introduce a Factory, Codec/Adapter, or Controller only where an existing cluster
of responsibilities already earns that boundary. No speculative interfaces,
service locator, dependency-injection framework, inheritance redesign, or
architecture layer is planned.

### 1.4 Explicit non-goals

Unless the user later amends this tracker, v1.1.0 architecture work must not:

- add user-facing features or change current easing behavior;
- change transition/ease enum numeric values;
- rename/remove public `EasingCurve` or `EasingCurvePoint` APIs;
- replace `EasingCurve` with a different public resource type;
- replace primitive snapshot dictionaries / packed arrays with serialized
  wrapper Resources or a second synchronized domain model;
- change serialized point-property names or storage keys;
- change public in-place `points` Array compatibility as part of cleanup;
- redesign point Handle Mode / Control State / Force Linear / Lock semantics;
- create a second point-state transition authority;
- rewrite `easing.gd`; it is large but cohesive equation-library code;
- redesign `EasingCurveEditor` graph input/drawing behavior unless required by a
  proven integration seam;
- reopen the already-resolved Autofit state-machine refactor without new
  evidence;
- introduce abstract interfaces solely for mocking or future speculation;
- combine unrelated cleanup, formatting, performance work, bug fixes, or feature
  work into an extraction step.

### 1.7 Design principles for all v1.1.0 extractions

1. **Façade stays stable.** Godot virtual callbacks and public entry points remain
   on `EasingCurve` / `EditorInspectorPlugin` when the engine requires them;
   those methods delegate to focused collaborators.
2. **Composition, not inheritance.** New helpers should normally be small
   `RefCounted`/data helpers or existing Control classes, owned explicitly by the
   current façade.
3. **One owner per rule.** Do not copy transition metadata, point-state rules,
   snapshot key definitions, or Undo policy into multiple helpers.
4. **Passive helpers where practical.** A codec should encode/decode/validate;
   the resource owns notifications. A state holder should hold state; it should
   not silently mutate the resource through hidden callbacks.
5. **No arbitrary LOC target.** The success metric is fewer reasons for each
   façade to change and clearer dependency direction, not reaching a line-count
   quota.
6. **Characterize first.** Add/strengthen focused coverage before moving a
   behavior whose contract is not explicit.
7. **One extraction per approved work item.** Close each item with focused tests,
   authoritative full-suite validation, cleanup, and diff review before moving
   to the next boundary.

## 3. Work Items

### 3.1 `ARCH-01` — Built-in Bézier preset geometry factory

**Status:** COMPLETE

#### Objective

Remove built-in Bézier point/control construction from the `EasingCurve`
resource while keeping the resource as the public façade and sole owner of
state mutation, notifications, global transform application, and compatibility
behavior.

#### Design diagnosis

The preset geometry branch is a real creation hotspot: `_update_preset()`,
`cubic_bezier()`, `cubic_bezier_pair()`, `_set_composed_bezier_preset()`, and
canonical-preset creation all change when built-in Bézier geometry changes.
This is the best first Factory-style extraction because it has a clear input ->
geometry output boundary and considerably less compatibility risk than moving
serialization first.

A simpler local-function cleanup would improve readability but would not remove
preset-geometry changes as a reason for the resource façade itself to change.
The focused factory therefore earns its boundary.

#### Scope

- extract built-in Bézier preset geometry construction behind one focused helper;
- keep transition/ease enums and authoritative `TRANSITION_DEFINITIONS` ownership
  on `EasingCurve` unless an approved step proves a smaller metadata owner is
  necessary;
- pass only the values needed to construct geometry (transition/ease and relevant
  parameter values);
- return newly constructed geometry without emitting notifications or mutating
  an existing `EasingCurve`;
- keep public preset methods and setters on `EasingCurve`, delegating internally;
- keep reverse/invert state ownership and notification semantics on the façade.

#### Non-goals

- no function-transition equation refactor;
- no `easing.gd` change;
- no enum/metadata duplication in the factory;
- no preset data format or approximation-value changes;
- no modified-preset UX change.

#### Architecture / risk assessment

**Risk:** low-to-moderate. The main regression risks are exact control geometry,
combined ease modes, Back overshoot scaling, endpoint count, and notification
ordering during preset changes.

The helper should be dependency-light and side-effect-free from the caller's
perspective. It should not receive the whole `EasingCurve` merely to reach
fields; explicit inputs make the boundary readable and testable.

#### Validation / acceptance requirements

Focused coverage should protect at least:

- `tween_equivalence_test.gd`;
- `easing_curve_transform_test.gd`;
- `easing_curve_v105_regression_test.gd`;
- preset-related checks in `runtime_curve_updates_test.gd`;
- built-in preset point counts/control geometry, including combined modes and
  Back overshoot;
- modified-preset detection/reset behavior;
- no duplicate/missing `changed` or `points_changed` behavior caused by the
  delegation.

Standard work-item closeout rules then apply.

#### Dependencies

Fresh release baseline and plan approval. No dependency on later v1.1.0 work.

#### Formal execution plan

```text

ARCH-01 Step 2 of 4 — Extract pure preset geometry construction
ARCH-01 Step 3 of 4 — Delegate EasingCurve preset creation through the factory
ARCH-01 Step 4 of 4 — Focused + full closeout and tracker update
```

- **Step 1:** identify any preset geometry / notification behavior not already
  directly covered and add only the missing characterization.
- **Step 2:** introduce the focused helper without changing public callers.
- **Step 3:** make the façade delegate built-in Bézier construction and remove

- **Step 4:** run focused tests, `git diff --check`, inspect scope, run the

### 3.2 `ARCH-02` — Primitive snapshot and dynamic serialization codec

**Status:** COMPLETE

#### Objective

Move primitive snapshot representation mechanics and dynamic point-storage
encoding/decoding out of `EasingCurve` while preserving the exact external
serialized and live-debug contract.

#### Design diagnosis

The current resource owns both domain/state orchestration and low-level
Dictionary/PackedArray schema mechanics. Snapshot key literals, typed arrays,
reverse/invert transforms, capture/restore helpers, diff/match helpers, and
storage-property path parsing are one compatibility-heavy cluster.

A Codec/Adapter boundary is justified because this representation must remain
stable while resource orchestration evolves. The existing
`easing_curve_point_snapshot_mutator.gd` remains the semantic Adapter from
snapshot data to the already-authoritative point-state transition rules; it is
not replaced by the codec.

#### Scope

- define one authoritative set of named `StringName` constants for existing
  semantic snapshot/storage keys without changing their text;
- centralize typed primitive snapshot creation/access/update helpers;
- centralize point snapshot capture and geometry transforms where doing so does
  not take ownership of notifications or topology;
- centralize representation validation only after characterizing the currently
  accepted legacy/partial forms;
- centralize dynamic point storage-name build/parse mechanics;
- let Godot-required `_get_property_list`, `_get`, and `_set` entry points remain
  on `EasingCurve`, delegating representation work to the codec;
- move function/editor snapshot *representation mechanics* only when they form a
  clear codec responsibility; keep setter ordering, state application,
  notifications, point identity restoration, and transition initialization on
  `EasingCurve`;
- update `easing_curve_point_snapshot_mutator.gd` to consume the shared schema
  boundary instead of growing another copy of key knowledge.

#### Explicit design constraint

Do **not** turn the codec into a second resource/domain model. It may understand
primitive representation; it must not own point-state policy, Undo/Redo,
notifications, editor selection, or runtime sampling.

#### Non-goals

- no serialized Resource wrapper for snapshots;
- no snapshot key/type renames;
- no migration format;
- no removal of backward-compatible default/fallback handling unless separately
  characterized and approved;
- no change to point Resource identity or topology rules.

#### Architecture / risk assessment

**Risk:** high. Serialization and Undo/Redo depend on exact dictionary shape,
array type, setter ordering, and resource identity behavior. This work item must
be more conservative than `ARCH-01`.

The clean-code goal is not to hide all dictionaries behind opaque methods. The
schema should become easier to trace, and the façade's orchestration should read
more clearly after the move.

#### Validation / acceptance requirements

Focused coverage should include:

- `serialization_transition_contract_test.gd`;
- `easing_curve_point_state_characterization_test.gd`;
- `editor_undo_redo_test.gd`;
- `runtime_curve_updates_test.gd`;
- `easing_curve_transform_test.gd`;
- exact snapshot keys, packed-array types, equal-length/legacy behavior, locks,
  Handle Mode, Force Linear, reverse/invert, and resource-order restoration;
- save/reload of current resources and established legacy fixtures;
- no changed public Inspector/live-debug property names.

Standard work-item closeout rules then apply.

#### Dependencies

`ARCH-01` complete, so preset construction no longer adds noise to the same
resource during this compatibility-heavy move.

#### Formal execution plan

ARCH-02 Step 3 of 5 — Extract point snapshot encode/decode/transform mechanics

#### Step 1 execution result — 2026-09-01

`ARCH-02 Step 1 of 5` is complete. This step was intentionally test/documentation
only; no production snapshot or serialization mechanics were moved.

Characterization added to
`test/scripts/unit/serialization_transition_contract_test.gd` now freezes the
compatibility forms that Step 2 must continue to accept:

- historical flat resources that omit Handle Mode and/or Force Linear fields
  load with Handle Mode `FREE`, Force Linear `false`, and normalized unlocked
  lock state when those fields are absent;
- a point snapshot whose topology is rebuilt from `positions` may omit
  `handle_modes`, `locks`, `left_force_linear`, and `right_force_linear`; those
  semantic fields fall back to `FREE`, unlocked, and `false` while complete
  position/left-control/right-control geometry is preserved;
- sparse dynamic storage writes such as `_point_2/position` grow the point array
  to the addressed index, and a partial `locked` Dictionary normalizes omitted
  lock members to `false`;
- function snapshots are patch-like: omitted parameters and generated arrays
  preserve their current values; generated arrays accept `Array`,
  `PackedFloat32Array`, and `PackedFloat64Array` input and normalize to the
  runtime `Array[float]` representation;
- editor-state snapshots are also patch-like for omitted scalar, Bézier, point,
  and function state: a present field is applied while omitted fields retain
  their current values.

Source inspection and runtime probes also found broader permissive behavior that
is **observed but deliberately not frozen as a compatibility guarantee**:

- an empty point snapshot currently clears topology because missing `positions`
  becomes an empty `PackedVector2Array`;
- missing/short control-point arrays can be accepted and may preserve or
  synthesize handle geometry depending on whether point Resources are reused or
  rebuilt;
- malformed generated-function array containers currently normalize through an
  empty `Array[float]`.

Step 2 must not tighten the characterized historical/patch forms above. It may
introduce a validation boundary for malformed/incidental forms only if the
validation remains compatibility-safe and does not alter current serialized
resources or editor/live-debug snapshots.

### 3.7 `EDITOR-03` — Inspector edit-transaction / Undo coordination controller

**Status:** IN PROGRESS — Step 4 of 5 COMPLETE

#### Objective

Consolidate Inspector gesture transaction capture/commit state behind a narrow
controller while preserving `EasingCurveEditorUndo` as the central editor-only
Undo/Redo adapter.

#### Design diagnosis

The Inspector currently owns draft `before` state, selection-before state,
point-resource IDs, action naming, drag/focus completion, point snapshot
mutation dispatch, final point-order commit, and calls into
`EasingCurveEditorUndo`. This is a real workflow/controller responsibility.

The existing `EasingCurveEditorUndo` is already a useful adapter around Godot's
Undo manager. Do not replace it. The new controller should orchestrate when an
edit begins/changes/finishes and assemble the existing ActionContext; the Undo
helper continues to translate that context into Godot Undo/Redo calls.

#### Scope

- draft edit lifecycle state;
- action naming;
- before/after state capture;
- selection and point Resource identity context collection;
- changing/final edit boundaries from spin sliders and graph gestures;
- point property mutation dispatch coordination;
- add/remove/reorder transaction commit orchestration where it reduces duplicate
  commit code;
- delegation to existing `EasingCurveEditorUndo`.

#### Non-goals

- no new Undo framework;
- no change to Godot action merge/commit semantics;
- no point-state rule duplication;
- no ownership of point-list rendering or graph drawing;
- no runtime editor dependency added to `EasingCurve`.

#### Architecture / risk assessment

**Risk:** high. Transaction boundaries are observable behavior and historically
regression-prone. The payoff is strong because this removes a major reason the
Inspector façade changes and makes edit lifecycle testable as one workflow.

Prefer one explicit controller with a small setup contract over Strategy/Command
class-per-action machinery. Existing action-name branching is not by itself a
reason to create a command hierarchy.

#### Validation / acceptance requirements

Primary focused suites:

- `editor_undo_redo_test.gd`;
- `easing_curve_editor_gesture_characterization_test.gd`;
- `easing_curve_editor_position_x_drag_test.gd`;
- point-list add/reorder suites;
- point-state characterization suites where transaction mutations touch semantic
  state.

Protect one Undo action per completed gesture, no action for no-op edits,
selection restoration, point Resource ordering, changing/final notification
publication, paste/reset/add/remove/reorder actions, and live Inspector change
forwarding.

#### Dependencies

`ARCH-04` and `EDITOR-02` complete so resource edit-session and selection
boundaries are stable before transaction extraction.
